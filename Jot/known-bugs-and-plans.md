## Sizing convention

Entries below carry a **size** tag using a T-shirt scale:

- **XS** — under 2 hours, single-file trivial change.
- **S** — 2-6 hours, single feature surface, 1-3 files.
- **M** — 1-2 days, multi-file but contained.
- **L** — 3-5 days, multi-component, real design decisions.
- **XL** — over a week, architectural change or new subsystem.

Sizes appear on the Known Bugs below and on aspirational entries that haven't shipped. Already-shipped features don't carry sizes.

## Known Bugs (Unresolved)

This section tracks user-facing bugs that are reproduced but not yet fixed. Each entry is a short symptom statement + the reproducer + the current root-cause hypothesis. Entries are removed when a fix lands and ships.

### Automatic cleanup stops working after a burst of keyboard dictations — ✅ FIXED 2026-09-25 (deferral)
**Owner-reported 2026-09-17 (build 307):** with AI cleanup on, cleanup worked for a while and then every dictation pasted as spoken with the amber "Cleanup didn't run" status. **Root cause:** Apple's on-device Foundation Model rate-limits apps running in the *background* — the framework docs state the `rateLimited` error "will only happen if your app is running in the background and exceeds the system defined rate limit" — and keyboard-dictation cleanup runs in Jot while it is backgrounded (kept alive by the mic). On iOS 27 each cleanup also spent two extra `tokenCount(for:)` requests deciding a cloud route that isn't usable yet. **Fix:** `RewriteClient` maps the error to `Failure.rateLimited` and never retries; the token-count calls are skipped while the cloud isn't usable; on a rate-limited cleanup `DictationPipeline` pastes the raw words at once and queues the transcript in `DeferredCleanupQueue`, which drains the next time Jot comes to the foreground and attaches the cleaned text to the note (row shows "Cleaning up" meanwhile); the keyboard status row says "Pasted as spoken — cleanup will finish when you open Jot". **Confirm on device:** reproduce with a burst of keyboard dictations, then Help → Diagnostics should show `REWRITE/FAIL` with `rateLimited: true`, followed by `CLEANUP/DEFER` and, after opening Jot, `CLEANUP/RAN` for the same transcript id, and the note's Rewrite tab filled in.

### Ask crashes the app (iOS 27, build 302) — MITIGATED 2026-09-14 (Ask hidden), root cause NOT yet confirmed
**Size: S.** **Owner-reported 2026-09-14** on iPhone 17 Pro / iOS 27 with build 302: opening or using Ask crashes Jot. No crash log yet — the phone was locked both times a `xcrun devicectl device info files --domain-type systemCrashLogs` pull was attempted (device "Vin", UDID `00008150-001151540C3A401C`); the owner can also share it from Settings → Privacy & Security → Analytics Data → `Jot-…ips`.

**What is established:** without Apple's managed Private Cloud Compute entitlement, `PrivateCloudComputeLanguageModel().availability` still reports `.available` on an eligible device, and every request THROWS `LanguageModelError -1` / `ModelManagerError 1046` (verified with an unentitled probe on this Mac, macOS 27). So Ask was visible on the phone with every question doomed to fail — but a thrown error is handled (`AskPipeline.describe`), so 1046 alone does not explain a crash. Not reproducible on the Mac: `_CoreSpotlight_FoundationModels` (`SpotlightSearchTool`) has no macOS module, so the tool-driven shape — the likeliest crash site (`SpotlightSearchTool`/`CoreSpotlightSource` over `TranscriptSpotlightIndex`, or the `searchResults` stream) — could not be exercised. Also seen in the probe: with `SpotlightSearchTool` + the help tool attached, an ON-DEVICE session's prompt is ~13.7K tokens (> the 8,192 on-device context) — so the Spotlight tool must never be used with the on-device model.

**Mitigation shipped in the branch:** `PrivateCloudComputeAccess.isEntitled = false` gates `AskController.availability()` (`.awaitingAccess`, entry point hidden, Siri phrase says "Ask isn't available in this version of Jot yet.") and `RewriteClient.cloudIsUsable` (no cloud fallback). **Next:** pull the crash log (unlock the phone, re-run the `devicectl` pull) and fix the real site before flipping the flag when Apple grants the entitlement (request at developer.apple.com/private-cloud-compute/ — Small Business Program + <2M first-time downloads).

### Keyboard: a blurred, washed band over the top line of a scrolling pane — ✅ FIXED 2026-09-15 (root cause found)
**Owner screenshots 2026-09-14 (Recents strip top row) and 2026-09-15 (live-text pane top line), iOS 27.** Root cause: iOS 26's automatic SwiftUI **scroll-edge effect** — content scrolled under a scroll view's top edge gets a progressive blur + wash. Both keyboard panes keep their content scrolled (the live pane auto-follows the newest words), so the top line always sat under the edge. Nothing in Jot drew it; the phone's move to iOS 27 made it appear inside the keyboard. Fix: `.scrollEdgeEffectHidden(true, for: .all)` on every scroll view the keyboard draws (`RecentsStrip` rows pane — 2026-09-14 — and `StreamingStrip`'s `StreamingPane`) and on the hero's live text, which has its own top fade. The 2026-09-14 crossfade change to the streaming ↔ recents swap stays (it is a good change on its own) but was not the cause.

### Vocab ask: pasted text ignored the "keep original" pick — ✅ FIXED 2026-07-15 (awaiting owner device-test)
**Owner-reported 2026-07-14:** answering a correction ask with the ORIGINAL word updated the saved transcript but the pasted text in the host app kept the corrected TERM. Two root causes, both fixed: (1) paste-holding asks could surface on the **post-paste** nudge path, which can only record a verdict — a keyboard cannot retro-edit another app's text; those asks are now gated to the pre-paste hold deck only (post-paste is reserved for the postPasteOnly merge-teach strip; a race-dropped ask stays reviewable on the transcript). (2) With AI-cleanup ON, the hold deck's strict splice anchor can drift a char and silently no-op; the resolver now falls back to an anchor-proximity-bounded (±48 chars), whole-word, **context-corroborated** unique match — failing safe on ambiguity, wrong-clause survivors, and removed words. Survived 4 adversarial Codex xhigh rounds (3×NOT CLEAN → CLEAN 97%); 19-case regression suite at `docs/harnesses/splice_check.swift` (re-run + re-sync its resolver mirror after ANY edit to `JotKeyboardViewController.spliceRange`/`contextCorroborates`). Inherent bound, documented in code: answers given on the post-paste teach strip and picks made later in the app can never rewrite text already pasted elsewhere.

### Keyboard Parakeet-upgrade nudge "Switch" dead-tap — FIXED; background download-on-charge ✅ BUILT 2026-07-14 (awaiting owner device-test)
**Plan: [docs/plans/parakeet-upgrade-nudge-download.md](../docs/plans/parakeet-upgrade-nudge-download.md)** (see its as-built + hardening sections). Recorded + primary bug fixed 2026-07-07; the enhancement was implemented 2026-07-14 (Wi-Fi+charging discretionary background fetch reusing the externalization pattern, auto-enable at a safe boundary, full sheet state machine incl. Stop-download/failed/lowDisk exits, home "You're on Jot's engine" card) and passed a 2-round adversarial review (7 findings + 3 NITs fixed, 2 accepted residuals documented). Atlas synced (v6). Needs on-device: real discretionary transfer + background-relaunch handoff, auto-switch at boundary, deep-link foreground tap.

**Symptom:** After using Apple dictation for a while, the keyboard shows the "More accurate dictation — switch to Jot's engine" nudge. Tapping **Switch** did nothing — the app didn't even open.

**Root cause (FIXED, awaiting owner device-test) — not a 258/stripping bug:** `handleParakeetNudgeUpgrade` opened `jot://upgrade-engine` via `extensionContext?.open(url)`, which iOS 18+ silently force-fails for keyboard extensions (see `openContainingApp`'s own doc, ~:2740). Broken on **every** iOS 18+ device on **every** build. Fixed by routing through the responder-chain opener `openContainingApp(url)` — the same one `jot://dictate` uses.

**After the app opens (already handled):** on a stripped build where Parakeet isn't on disk, flipping `useAppleDictationForEnglish = false` is NOT a dead-end — the next Parakeet dictation hits the download-on-first-need backstop in `TranscriptionService.loadOrFail` (`!modelsOnDisk → .downloading` → fetch v2 → load; the §C jumped-to-stripped path).

**Remaining enhancement (owner ask, NEEDS VALIDATION):** make Switch *proactively* download on eligible devices (`parakeetUsable`) via a **background, charging-gated** fetch + user message ("we'll download while charging and switch you automatically") + **auto-enable on arrival** (safe boundary, never mid-recording), rather than lazy download-on-next-dictation. ### Latent: a failed corrections-ledger load silently wipes it on the next save
**Size: XS.** Found 2026-07-16 by the vocab-core design review (elaborated in `~/code/jot-shared/docs/design-vocab-core.md` §Q-3). If `corrections.json` ever fails to decode, the store starts empty and the next save persists the empty ledger — a total, silent wipe of the user's curated correction history (per-transcript provenance is better isolated: one corrupt file loses one transcript). Never observed in the wild; pure timebomb. **Fix:** the store must refuse to save over a file it failed to load (keep the failed file, surface a diagnostic). Lands either with the shared vocab-core package (which carries it as a required roundtrip fixture) or as a standalone one-guard change in the next batch — whichever ships first.

### Auto-paste silently fails in some host apps (notably Slack)
**Size: M. Status: ✅ FIXED via PROXY RE-SYNC — build 108 (confirmed on-device).** **Plan: [docs/plans/bug-slack-silent-paste.md](../docs/plans/bug-slack-silent-paste.md).** The REAL root cause (Update #9) is host-dependent: a cold `insertText` no-ops into a custom/web compose field (Claude/Slack) that re-mounted during the record→transcribe gap, leaving the proxy's input connection stale — works in native fields (Messages). Builds 104/105 (notification-race fix, Updates #6–#7) were an earlier, different chapter that 106 regressed. **See Update #9 below for the definitive cause + fix.** **NB history: build 103 made it worse; 104/105 fixed the notification race; 106 ("land once") regressed host-paste; 108 re-sync fixes the actual stale-proxy cause.**

**Symptom:** Stop a warm-hold dictation while focused on a host app's text field (observed in Slack). The keyboard's `pasteSuccess` event fires in the diagnostics log with the full character count, but no text appears in the host field. The dictated transcript is still stored in Jot's library — only the auto-paste step silently no-ops.

**When it happens:** Warm-hold path (Jot never foregrounded). Most reliably observed with Slack as the host; possibly other apps with custom JS-backed compose fields or draft-autosave systems. Intermittent rather than every time.

**Why `pasteSuccess` is misleading:** `UITextDocumentProxy.insertText(_:)` is a void call — it returns nothing whether the host accepted the insert or not. The "pasteSuccess" log line confirms only that the keyboard *called* the function, not that any text actually landed in the host's text field. The host can silently reject the insert if the proxy is mid-disconnect, if the keyboard isn't the active input view at the moment of call, or if the host's text-input delegate rejects programmatic inserts.

**Current hypothesis:** the host's textDocumentProxy is disconnected (returns `nil` for `documentContextBeforeInput`) at the moment of insert, so iOS no-ops the call silently. Slack's compose field has known unusual focus + draft-autosave behavior that may transiently break the proxy connection. As of build 4 the `pasteSuccess` log now also captures `proxyHadContextBefore` + a before/after context-length delta so the next failure produces actionable signal: if `contextGrew` equals the inserted character count, the host accepted the text; if it's `0` or `-1`, the insert was silently dropped. Once a failure is captured with the new instrumentation, the fix (likely gating insert on `proxyHadContextBefore == true` and posting an error banner otherwise) becomes a one-liner.

**Update 2026-06-05 #6 — ✅ FIXED & SHIPPED (build 103). #5's "silent insert-drop" was ALSO wrong — `contextGrew` is a false negative on long pastes.** A clean 4-stop log settled it: `documentContextBeforeInput` returns a bounded, line-reset window, so a long/multi-line insert makes the reported pre-caret context SHRINK even though the text landed (owner confirmed the 309-char `contextGrew=-256` stop "this time it pasted"). The genuine failure had **no `pasteSuccess` at all** — the insert never ran. **Real root cause:** the auto-paste flush (`flushPendingAutoPasteIfPossible`, does NOT gate on phase) is driven ONLY by `pipelinePhaseChanged`. In the publish sequence (`DictationPipeline` fresh branch) the ONLY phase post that fires AFTER the payload is written is the terminal `publishPipelinePhase(.idle)` — which also calls `stopHeartbeat()`, so it's the LAST notification for the session. Darwin posts of the same name coalesce; when that single `.idle` post is coalesced/dropped (it trails a same-named burst + an `await transitionPostPublish`), the flush never re-runs, the heartbeat is already off → the published payload sits unread forever. One missed notification = permanent silent loss → intermittent. Proof: failing stop `558E7EEF` logged `publishCompleted` then total silence (heartbeat stopped = `.idle` ran, but its notif didn't wake the flush); identical-shape `E07DED06` got the `.idle` flush 4ms later → pasted. **Fix (`JotKeyboardViewController`): also drive `flushPendingAutoPasteIfPossible()` from a `transcriptReady` observer.** `transcriptReady` is posted the instant the payload is written (no await), in the live notification window — a reliable "transcription done → paste" trigger; `.idle` stays as backstop; double-flush is idempotent (`markConsumed` + `clearPendingPasteSession`). The old "don't observe transcriptReady → stale recents" objection applies only to the history mirror, not paste (payload already written). Build 103 → TestFlight (UPLOAD SUCCEEDED). **All prior theories here (suspension #3, publishCompleted-stall #4, insert-drop #5) were wrong — the bug was a coalescing race on the single post-payload notification.**

**Update 2026-06-05 #7 — ✅ DEFINITIVELY FIXED (build 104), confirmed on-device. #6's mechanism was right but its `transcriptReady` fix (build 103) MADE IT WORSE.** A build-104 on-device experiment (fire the insert on every trigger, tag each with which trigger + whether it landed, and keep the transcript until one lands) gave the clean answer: a single stop logged `trigger=transcriptReady` → `proxyHadContextBefore=false, landed=false` (proxy NOT connected at the early moment), then ~4ms later `trigger=pipelinePhase` (settled `.idle`) → `proxyHadContextBefore=true, contextGrew=50==chars, landed=true` LANDED. Single trigger = zero double-paste risk (no cap needed). Ripped out the experiment scaffolding (6-attempt cap, attempt counter, `isAutoPasteFlushing` re-entrancy flag, `textDidChange` retry trigger, and the `trigger`/`landed`/`attempt` diagnostic metadata). The not-landed case now logs under `pasteSkipProxyDisconnected`. `contextGrew` is no longer trusted as the success oracle (false-negative on long/multi-line pastes — `documentContextBeforeInput` returns a bounded, line-reset window); `proxyHadContextBefore` is primary.

**Update 2026-06-08 #9 — ✅ FIXED via PROXY RE-SYNC (build 108), confirmed on-device. The 104/105 fix (notification race) was a real but DIFFERENT bug; build 106 ("land once, reliably") regressed host-paste and exposed the ACTUAL root cause.** Owner symptom that cracked it: auto-paste fails in **Claude's app + many apps but WORKS in Messages**, and at stop the field is provably LIVE (cursor blinking, transcript already shown in keyboard recents). So it is NOT a dropped notification and NOT "stale because the user navigated away" — it is a **host-dependent insert no-op**. Mechanism (corroborated by FluidAudio source + Apple docs + our own coalescing code): the transcript arrives ~hundreds of ms after Stop (record → transcribe → cross-process publish), NOT inside a UI event; in that gap a **custom/web compose field (Claude/Slack = React-Native/WKWebView) re-mounts its text view**, so `textDocumentProxy` points at a stale input connection — the pointer still looks valid and the caret still blinks, but a **cold `insertText` silently no-ops**. A native `UITextView` (Messages) keeps the connection, so it always lands there. There is **no iOS API to keep another app's field/proxy alive** (a keyboard extension is handed a proxy, never the field) — confirmed via research; the only lever is to RE-SYNC before writing. **Build 108 fix (`flushPendingAutoPasteIfPossible`):** issue `adjustTextPosition(byCharacterOffset: 0)` (caret unchanged) to force the host to re-establish the input connection, then **yield ONE run-loop tick** (`DispatchQueue.main.asyncAfter +0.012`) BEFORE the insert — because iOS COALESCES `adjustTextPosition` into the current UI cycle (our `moveUpStep`/`moveDownStep` already proved a synchronous nudge gets swallowed), so a sync nudge-then-insert still hits the stale link. A new `isAutoPasteInsertInFlight` guard covers the ~12ms window so a second phase-change flush can't stack a duplicate → **single insert, no retry band-aid** (owner explicitly rejected retry as a "double-charge"). Logs now carry `resynced=true`. The build-106 landed-detection (`proxyHadContextBefore || proxyHasContextAfter`, keep-pending if not landed) is preserved as the safety net.

- **One encoder, ~582 MB.** Streaming and batch use *different* encoders but SHARE decoder/joint/preprocessor/vocab, so a user who already pulled the batch variant (builds 292/293) only pays for the streaming encoder (~564 MB). Both encoders resident would be ~1.1 GB — avoided by using streaming for live text *and* the final.
- **Promotion, not re-transcription.** `unifiedEnglishPromote` reuses the existing **D2 promote** contract (`stopArtifact()` → `depositStreamingArtifact` → stop-pass skip) that `appleStopPass` already uses. `RecordingService.tearDownStreamingSession` calls `quiesce()` then `stopArtifact()` on the `StreamingSession` protocol — engine-agnostic, so no plumbing was needed. Promotion requires an EXACT sample-count match, so a pause-slice or dropped chunk falls back to the normal engine instead of saving a short transcript.
- **`makeStreamingSession` also had to be forced.** `stopPassTranscribe` checks unified BEFORE `useAppleEngine`, so on a device with "Use Apple speech engine" ON the final would have been unified while the live preview came from Apple — the user watches Apple's words, then receives different ones. Found only because the owner pushed back with "are you sure?" **Fixed properly in 297:** the streaming factory now branches in exactly the same order as the stop-pass and returns the native `UnifiedStreamingSession` when `isActive` — `PreviewScheduler`/`previewTranscribe` are not on this path at all (an earlier note here claimed `previewTranscribe` carried a matching unified branch; it never did — that described the abandoned batch design).

No model on disk falls through to the standard engine instead of failing. Unlike the Apple/Parakeet split (where cross-engine fallback is forbidden by owner directive), a unified failure **does** fall back — it is an opt-in experiment layered on a working engine, so it must never cost a real dictation.

### Teach a vocabulary term by voice — v2, the sentence test (BUILT 2026-08-31, awaiting owner device-test)

- **Teach by voice v2 — ✅ BUILT 2026-08-31 (UNCOMMITTED, awaiting owner device-test).** **Size: M.** Design: [docs/plans/teach-by-voice-v2.md](../docs/plans/teach-by-voice-v2.md) (v2.1, adversarially reviewed — findings and file:line evidence in [teach-by-voice-v2-REVIEW.md](../docs/plans/teach-by-voice-v2-REVIEW.md)). Code: `App/Vocabulary/TeachSentenceLocator.swift` (new), `App/Vocabulary/TeachVocabularyByVoice.swift`, `App/Settings/VocabularySettingsView.swift`, `App/Vocabulary/VocabularyStore.swift`, `App/Transcription/TranscriptionService.swift`, `App/Ask/AskView.swift` (`FlowLayout` made shared). Docs: [features.md §8.4a](features.md#8-4a-teach-a-term-by-voice).
- **Supersedes build 296, which failed because Jot graded itself.** 296 re-implemented the gate's common-word rule inside the teach flow, inverted ("Cloud code" ✅, "Claude code." ❌), and spent attempts on the wrong verdicts. The v2 invariant is structural, not a bug fix: **Jot never classifies a take as right or wrong — it applies, shows, and asks.** The verdict taxonomy (`.term/.known/.unusable/.formattingNoOp` as user-facing judgments), the `maySave` gate computed from it, and the attempts-exhausted mechanic are all deleted; with no grading there is nothing to exhaust. What survives from 296 is the part that was right: the session/recorder lifecycle (incl. the `hasDismissed` mic-ownership latch), the take-list UI skeleton, `mergeAliases`, and Cancel/Save.
- **Phase 2 is the whole idea: validate against a REAL dictation.** Learning a mishearing was never the hard part — knowing whether the learned vocabulary actually FIRES was, and isolated repetition can't answer it (words sound different mid-sentence). After ≥2 takes the user says a natural sentence, transcribed by the production pipeline with the provisional aliases already applied.
- **It reads the pipeline's PROPOSALS, not its final text (review BLOCKER-1/2).** `VocabularyGate` deliberately BLOCKs applying a term over an everyday-word original and surfaces an ask instead — which is exactly the design's own acceptance case ("Vineet" heard as "we need"), so a final-text locator would report failure forever on the one case picked to prove the feature. New `TranscriptionService.transcribeWithProposals(samples:)` returns `(text, gatedText, proposals)` — what `runInference` already computed and discarded — and the sheet renders **three descriptive states**: applied / *found but held back* / not found. None is a grade.
- **Spans are mapped, then re-validated.** A proposal's `publishedStart` is valid for `gatedText` ONLY; the segmenter, filler sweep, number pass and punctuation model all rewrite the text afterwards (the punctuation model strips and re-adds case wholesale). Offsets move through `CorrectionProvenance.mapOffsets` and every span is re-checked against the sentence — a drifted span degrades to not-found (or to a verbatim hit when the term really is there), never to a wrong highlight. Comparison is `CorrectionKey.normalize` throughout, never raw equality.
- **Provisional aliases are persisted then rolled back (review Q1/finding 5).** An overlay is infeasible: the model-free corrector reads the store in memory while the acoustic path reads the FILE. **Every** sentence recording — not just the first — writes them and **awaits** the rescorer rebuild via the new `VocabularyStore.updateAwaitingRescorer`; `save()`'s rebuild is fire-and-forget with no completion signal, and `awaitReady` can't stand in because `isReady` is already true for the stale vocabulary. Per-record rather than per-phase-entry because the owner's spec ends with "the user updates it: *THIS* is what it is" → try again, and a retry running against the pre-correction vocabulary would validate the wrong thing; a persist that would write nothing new is skipped, so a plain re-record pays nothing. Cancel restores the pre-teach alias array; Save merges onto that same pre-teach base so a take deleted after phase 2 doesn't survive.
- **A swipe-down no longer discards a session silently.** It was the same discard the Cancel button performs with none of its intent. When there is anything to lose the gesture is refused and explained — Discard / Save what I taught / Keep teaching. SwiftUI's `interactiveDismissDisabled` refuses but offers no callback, so `SheetDismissGuard` bridges UIKit's `presentationControllerDidAttemptToDismiss`; it CHAINS to the delegate it displaces (SwiftUI's own, which resets the `sheet(item:)` binding on a real dismissal) rather than replacing it, and forwards `shouldDismiss` when not blocking plus the two adaptivity callbacks (invisible on iPhone portrait, load-bearing on iPad). Cancel stays an explicit, immediate discard. **Gotcha worth keeping:** the guard rides in a `.background`, so it is a CHILD view controller, and `UIViewController.presentationController` resolves through the presented/presenting chain, NOT through containment — it is nil on the child. The first version guarded on `self.presentationController` and therefore never installed at all (swipe discarded silently, and the reopen tests "passed" only because nothing had been displaced to chain to). It now walks `parent` to the topmost ancestor first. Simulator-verified end to end: clean swipe dismisses, swipe-with-a-take is refused and shows the dialog, Discard rolls back and the sheet reopens fresh.
- **The user's answer to a sentence run is four-valued, not a boolean.** "Yes, that's it", "nothing here matched" and "I just taught you the right words" are different answers; collapsing them made Jot reply to a rejection with a green *"Your vocabulary is working in a real sentence."*, and made a successful tap-correction read as if nothing had happened (the learned form is now named back: *"'we need' added to Sounds like"*, with "Pick more words" for a second wrong span in the same sentence). Going back to phase 1 also clears the previous run outright — re-entering re-persists a possibly different alias set, so a kept highlight would be describing what a *different* vocabulary did.
- **Per-keystroke rescorer rebuild fixed (review MINOR-18, now applied to the TERM field too).** Every term-field keystroke writes through `VocabularyStore.save()`, and each rebuild is a full `VocabularyRescorer.create` (CoreML) — a ten-character term queued ten of them, nine of which the holder's `generation` guard discarded after paying for them. `save()`'s rebuild is now debounced 400 ms and single-flight; `updateAwaitingRescorer` cancels any pending one first, so a stale keystroke rebuild can't land mid-recording and win the generation arbitration.
- **Diagnosable from the device (Help → Diagnostics, `.vocabularyGate`).** The sentence run records its outcome, proposal counts (total and for-this-term), span count, whether the post-gate text drifted, and the length; each persist records the alias counts and the measured rebuild time. The owner's device pass is the only verification this feature gets, so it has to be readable afterwards rather than only from a live Console.
- **Known gap in the entry gate — Belarusian.** `isVocabEligible` is true for it, so the teach button shows, but `commonWordsResource` is `nil` (no reliable frequency data, `LanguageChoice.swift:123`) ⇒ `correctorLanguageCode` is `nil` ⇒ the model-free corrector never runs, and the acoustic scorer is a Latin-script checkpoint. The sentence test is therefore structurally not-found there. Not gated on: the pair the button checks is deliberately the same pair the transcription path checks, and inventing a third condition here would put the gate and the apply out of sync. Note it, revisit if a Belarusian user ever appears.
- **Entry gate added (review MAJOR-3 — there was none).** "Teach it by voice" showed whenever the term text was non-empty. Phase 2's vocabulary apply is gated on `VocabularyStore.isEnabled && LanguageChoice.current.isVocabEligible`, so without the same gate the sentence test reports not-found 100% of the time on CJK / LatAm-Spanish or with the master toggle off. The button now checks that exact pair.
- **The "Sounds like" affordance fix ships with it (owner: it "doesn't look like it's editable").** The comma-separated caption became deletable chips + an "add a misheard form…" field, shown for **every** non-empty term rather than only ones that already have aliases. Side benefit: the comma editor wrote through on every keystroke, and each write rebuilds the CoreML rescorer — chips commit on return instead.
- **Engine parity: asserted, not coded (review finding 8).** The teach sheet claims `ownsActiveRecording`, which exempts it from the live-text preview gate — so with "Live text while dictating" OFF it could have validated on Parakeet Unified while the user's real dictations fell back to v2.
