# Jot — ARCHITECTURE

## Orientation

Fresh-session read order: the auto-loaded agent working-rules (your global rules + this repo's project rules) → auto-memory `MEMORY.md` (hard-won facts + feedback) → `Jot/known-bugs-and-plans.md` (registry of bugs + `docs/plans/*`) → `Jot/features.md` (the WHAT — exhaustive feature behaviour) → **this file** (the WHERE — coarse code map) → the code.

This is a stable, coarse code map at subsystem granularity: a bird's-eye view, where each subsystem lives, the boundaries/invariants that reading code won't reveal, and searchable starting symbols. It is **not** a feature spec — it deliberately does not restate feature prose; it links `features.md §` sections instead. It is sized to survive refactors, so it names subsystems and contracts, not individual functions or line numbers.

**Visual map.** A browsable mockup of every UI screen lives in `atlas/` — a self-contained static site (vanilla HTML/CSS/JS, no deps): `atlas/gen/index.html` is the viewer (light/dark, device-size presets), `atlas/gen/frag/<id>.html` are per-screen fragments generated from the real `JotDesign` tokens, and `atlas/atlas.json` is the screen↔`features.md §` join table (also records the `JotDesign.swift`-sourced device dimensions). Real device screenshots live under `atlas/screens/` (local only — they contain personal data and are **not** deployed). Use the atlas to point at a screen when discussing a change; it is a reference map, not a source of truth — `JotDesign.swift` + the SwiftUI views remain authoritative for pixels.

## Bird's-eye view

Jot ships **five runtime processes** — main app, keyboard, share extension, watch app, and watch widgets — but only **three share the App Group**: the main app, the keyboard, and the share extension. (The watch app + widgets are separate watchOS targets that couple to the phone over WCSession, NOT the App Group — they carry no `application-groups` entitlement.) The subsystems below are the App-Group / WCSession handoff path:

- **Main app** (`Jot` target; app-only code is gated `#if JOT_APP_HOST`) — owns the single SwiftUI scene, the SwiftData store, every service singleton, and all model inference (Apple dictation via SpeechTranscriber/DictationTranscriber, Parakeet ASR, and Apple Foundation Models — the on-device model plus, on iOS 27, Private Cloud Compute for Ask and long rewrites). It also owns the Core Spotlight projection of every transcript (`TranscriptSpotlightIndex`), which is both system search and Ask's retrieval substrate.
- **JotKeyboard extension** — a separate process with a **~60 MB memory ceiling**. It **must not link FoundationModels or FluidAudio**, and **must never open SwiftData**. It is dictation-only (no QWERTY): it drives recording in the main app by remote-control and inserts finished text into the host field. (Because **`FluidAudio` can't link into the keyboard OR the watch**, the dictation **language** must be readable WITHOUT it: the cross-process source of truth is the plain-string `AppGroup.transcriptionLanguage` key (`jot.transcription.language`), and the app's `LanguageChoice` — which DOES import FluidAudio for its script hint — has Foundation-only mirrors (`WatchLanguage` for the watch; the AppGroup string for the keyboard).)
- **watchOS app** (+ widgets) — records audio locally and ships it to the phone for transcription; receives a read-only top-10 list back. It can also **pick the dictation language** locally (Digital Crown) and tag its audio with it.

The **only cross-process channel is the App Group** (`group.com.vineetu.jot.mobile.shared`): UserDefaults keys + JSON projections/mirrors for state, and **Darwin notifications as signals only** (they say "re-read the projection", never carry truth). The keyboard reads transcript history from a JSON **mirror**, never SwiftData. The watch couples over **WCSession**, then merges into the same shared store on the phone.

The **SwiftData store lives inside the App Group container** (`JotTranscripts`, `cloudKitDatabase: .none`), on a **frozen versioned schema** (V1→V9) with a Flyway-style migration plan. The store and its container are main-app-only even though the schema files compile into both targets. **Watch-target gotcha:** the `JotWatch` target ENUMERATES each `Shared/Schema/JotSchemaVN.swift` explicitly in `project.yml` (not a `Shared/` glob), so **every new schema version must be added to that target's `sources:` list by hand** or the watch build breaks.

Speech-model **weights** live under `Library/Application Support/<vendor>/` (sticky — survives memory pressure, NOT Caches) and are recursively flagged `isExcludedFromBackup` via `BackupExclusion` (run in `JotApp.init`) so the ~2GB re-downloadable weights stay out of iCloud Device Backup. The same `JotApp.init` sweep also backup-excludes the **3-day source-audio retention** store (`RetainedAudio/`, App Group container; see `RetainedAudioStore`). The SwiftData transcript store is a separate residency (App Group container, above).

The sole off-device transmission is the **user-initiated feedback POST** (plus a read-only donations GET); everything else is fully on-device.

## Subsystem notes

### App entry & lifecycle
**Role.** Process startup, the single SwiftUI scene, URL-scheme routing, scenePhase-driven lifecycle (foreground heartbeat, model warm-up, BG task submission), and the capture-first auto-start state machine that turns a keyboard's `jot://` bounce into a live recording.
**Entry points.** `triggerAutoStart`, `onOpenURL`, `handleSceneActive`, `startForegroundHeartbeat`, `presentExternalKeyboardHeroIfPending`, `updateDictateTapObserver`, `CrossProcessRecordingStopCoordinator.handleStopRequested`.
**Invariants.**
- `JotApp.init()` does **no blocking I/O** — only constructs service singletons and posts non-blocking warm-up Tasks; warm-up / mirror refresh happen in the scene `.task` on first activation.
- `RecordingService` / `TranscriptionService` are process-wide singletons (`.shared`) injected via `@State`+`@environment`; headless intents reuse the SAME `.shared` — never construct second instances (audio-session prior-state leak before v10).
- Auto-start is **once-per-session**: `triggerAutoStart` consumes `autoStartConsumed` FIRST, even on every bail, so a resume-from-background never silently retries; only an explicit `jot://` open or the deferred `.onChange` retries re-fire it.
- **Capture-first cold start**: if the model isn't ready, kick `warmUp()` but start the mic NOW so nothing said during the ~30s cold load is lost; the model is awaited at stop time, not start.
- scenePhase teardown (heartbeat clear) happens ONLY on `.background`, never `.inactive` (a Jot keyboard/banner/Control Center briefly makes Jot `.inactive` while effectively foreground).
- **NEVER forceStop on `.background`** — `audio` background mode keeps the mic live so swipe-back-to-host recordings survive.
- Foreground heartbeat ticks faster (1s) than `AppGroup.isJotAppForeground()`'s 2.5s window, with one synchronous write at start so the first keyboard read isn't stale.
- Save/no-save is decided at the STOP site: `stopAndPublish` gates on `applicationState == .active` SPECIFICALLY (not `!= .background`).
- `PipelinePhaseProjection` is the SINGLE cross-process source of truth for recording state; `JotApp.init` must call `PipelinePhaseProjection.reset()` on launch — this alone also clears any leftover warm-hold (`.warmIdle`) record from a crash mid-warm (warm-hold never auto-activates on cold launch), covering what the legacy `warmHoldExpiresAt`-on-launch clear did before B4.
- `ownsActiveRecording` is the generic "an in-app surface OWNS this recording" signal (stop-routing bails, warm-hold-nudge ring skips, return pill suppressed, interruption-publish gated). THREE sanctioned claimants: Ask's `InlineDictationSession`, the rewrite picker's voice-prompt capture (`RewritePickerSheet.VoicePromptCapture`), and the vocabulary teach-by-voice sheet (`App/Vocabulary/TeachVocabularyByVoice.swift`). Every NON-owning start path must defensively clear `ownsActiveRecording=false` before `start()`; a claimant must clear it on every terminal.
- `onOpenURL` branches on `url.host`: rewrite/history/transcript are handled-and-returned WITHOUT auto-start; only the dictate/plain fall-through calls `triggerAutoStart`.
- Hero presents from exactly 3 triggers (FAB, cold `jot://dictate`, return pill); nothing adopts `isRecording`. In-Jot `keyboardDictateTapped` starts a background capture and presents NO hero.
- Use `.modelContainer(JotModelContainer.shared)` — NOT `.modelContainer(for:)` (headless intents write without a scene).
**Blast radius.** Sits above everything: the only scene + SwiftData container, the service singletons every surface reads via `@environment`, and the URL/Darwin front door. A regression here (init I/O, wrong scenePhase gate, stale projection) breaks cold-launch dictation, cross-process keyboard handoff, and auto-paste app-wide.

### Recording & capture
**Role.** The microphone lifecycle — start/stop/pause/resume/cancel, the live streaming tap, warm-hold mic retention, and the full-screen recording hero UI with its cold-start model-loading affordances — feeding audio into the transcription pipeline.
**Entry points.** `RecordingService.shared/.start()/.stop()`, `AudioTapRouter.beginSlice`, `RecordingHeroView (HeroPhase)`, `ModelLoadTimekeeper.estimatedSeconds`.
**Invariants.**
- `RecordingService.shared` is a process-wide `@MainActor` singleton — exactly one `AVAudioSession` per process; never construct a second instance for real capture.
- `streamingQueue` MUST be allocated BEFORE `installTap` (closures capture it); teardown always nils `streamingQueue` LAST.
- Never `forceStop()`/`discard()` to release the mic — use `stop()`/`stopGently()`/`cancel()` so Warm Hold is honoured. (W6 wizard teardown also uses the gentle `cancel()`, NOT `forceStop()`.)
- Pause is a sub-state of an active recording: `isRecording` stays true while `isPaused`; cannot pause while warm-held (warm-hold is a post-stop idle state).
- "End the transcription" and "release the mic / warm-hold" are SEPARATE axes; a transcript saves only when stopped OUTSIDE Jot or from the hero.
- Cold-start capture begins buffering the instant the user taps, BEFORE the speech model loads (`HeroPhase.preparing`).
- Hero presentation is **source-based** (FAB / cold `jot://dictate` / return pill); the "adopt-unless-vetoed" model was deleted.
- `ModelLoadTimekeeper`'s bar is NOT a byte percentage — it's paced against this device's prior measured load duration and eases-then-waits past the estimate.
- Warm-hold publishes through `PipelinePhaseProjection`'s `.warmIdle` phase, carrying `warmExpiresAt` plus a ~1s `liveness` stamp (the legacy separate `warmHoldExpiresAt`/`warmHoldHeartbeat` AppGroup keys were removed in B4); a stale liveness stamp reads as expired; publication defers until `markPipelineFinished` if a pipeline is in flight.
- `InlineDictationSession` (the TYPE) remains Ask-exclusive. The rewrite voice prompt deliberately does NOT use it — `VoicePromptCapture` (in `App/Rewrite/RewritePickerSheet.swift`) replicates its four lifecycle invariants against the raw `RecordingService`/`TranscriptionService` primitives and claims `ownsActiveRecording` the same way. `VocabularyTeachingSession` (in `App/Vocabulary/TeachVocabularyByVoice.swift`) is the third such replication — same reason, same invariants: it releases on start failure, on both the success and stop-failure branches of a take, and on dismissal-mid-capture (which awaits the in-flight start Task before a gentle `stop()`), with an `isTearingDown` guard because cancel-then-dismiss fires teardown twice.
- The teach sheet is also the only claimant that does NOT want the live preview it is nonetheless given: the preview-on gate below always starts the scheduler for an owned capture, so a short teach take spins up batch pseudo-streaming whose output is discarded (`streamingPartial.reset()` on teardown). Harmless, but do not "optimise" it by un-owning the capture — ownership is what keeps the stop-routing, warm-hold nudge and interruption-publish from treating a teach take as a real dictation.
- **Teaching's provisional aliases are PERSISTED then rolled back, not overlaid.** The two vocabulary paths read different sources — the model-free corrector reads `VocabularyStore.shared.terms` in memory, the acoustic path reads the FILE via `CustomVocabularyContext.loadFromSimpleFormat` — so an in-memory overlay tests half the pipeline. Entering phase 2 writes the merged aliases through `VocabularyStore.updateAwaitingRescorer` (the awaitable sibling of `save()`, whose rescorer rebuild is an unstructured fire-and-forget with no completion signal, and whose `awaitReady` cannot substitute because `isReady` is already true for the STALE vocabulary); Cancel/dismiss restores the pre-teach alias array. A crash mid-teach strands real observations, which are deletable chips in the term's Sounds-like row.
- Interruption-publish contract: an audio-session interruption (call/Siri/route change) publishes the captured audio through the normal pipeline ONLY for un-owned captures (real dictations should still deliver); when `ownsActiveRecording` is true the publish is skipped — the owning surface (Ask, voice prompt) handles its own failure UX, and an interrupted inline capture must never save a transcript or touch the clipboard.
**Blast radius.** Upstream callers: ContentView (in-Jot tap), JotApp (warm-resume + auto-start), RecordingHeroView (FAB), DictateIntent, SetupWizardView (W6), Ask. Downstream: feeds `StreamingBufferQueue → PreviewScheduler` (live preview) and `TranscriptionService`/`DictationPipeline` (final); publishes phase via `RecordingPipelineDispatch`/`PipelinePhaseProjection` + `pipelinePhaseChanged`. The `PipelinePhase` enum lives in `Shared/`, not here.

### Transcription & ASR models
**Role.** On-device speech-to-text via **two peer engine families, selected by language + hardware — NOT a user picker.** (1) **Apple's on-device dictation is the DEFAULT** for every language it supports (English + es/fr/de/it/pt + ja/ko/zh/yue — `LanguageChoice.isAppleSupported`/`appleLocaleIdentifier`). Under it are TWO concrete Apple engines chosen by `TranscriptionService.appleEngineIsSpeechTranscriber` (= `SpeechTranscriber.isAvailable`): the modern, hardware-gated **`SpeechTranscriber`** (~A17/M1-class+), else the older broad-compat **`DictationTranscriber`** (e.g. the 2020 A12Z iPad Pro, which can't subscribe to `SpeechTranscriber`'s model) — so on-device Apple dictation works on devices where Parakeet can't run. Both stream natively (`AppleStreamingSession` / `DictationStreamingSession`, `StreamingSession` protocol) and finalize via a one-shot (`AppleDictationEngine` / `DictationOneShotEngine`). (2) **Jot's own FluidAudio Parakeet** is the higher-accuracy UPGRADE (opt-in via the keyboard nudge; `AppGroup.useAppleDictationForEnglish` default `true`) AND the ONLY engine for the ~18 European languages Apple can't do. **English** → **Parakeet Unified 0.6B** (`UnifiedEnglishModel`, English-only checkpoint, natively streaming, downloaded — see the Unified bullet) once it is on disk AND loaded, else the **Parakeet 0.6B v2** it supersedes (`AsrModelVersion.v2`, `Resources/Models/Parakeet/parakeet-tdt-0.6b-v2/` — NO `-coreml`; carried into shared storage for upgraders / downloaded on demand otherwise, stripped from the IPA by default — see the model-externalization bullet), which remains the pre-download fallback and cannot be deleted; a **Parakeet-only European language** → multilingual **Parakeet Ultra** (`AsrModelVersion.ultra` — moondream post-training of v3, same decode path; replaced v3 2026-09-27), NOT bundled, `AsrModels.download(to:version:)` → FluidAudio App-Support cache). Parakeet runs ONLY where `TranscriptionService.parakeetUsable` (= `DeviceCapability.is600MCapable && DeviceCapability.parakeetTierDevice`, i.e. iPhone 14 Pro+ / iPad M1+); elsewhere Apple is the only engine. The 110M `parakeet-ctc-110m` is the bundled **vocab CTC scorer** — a SEPARATE model, NOT a dictation model. On the Parakeet path the live preview is produced by **re-transcribing a trailing audio window** (`PreviewScheduler` → `previewTranscribe`) and the same model finalizes on stop — EXCEPT English-on-Unified, which streams natively and promotes (below); the Apple path streams the preview natively and, when its streamed text fully covers the recording, PROMOTES it as the saved transcript (no re-transcribe — the "D2 promote"). Which device-supported languages a picker may show comes from `DictationLanguageAvailability` (asks the ACTIVE Apple engine's live `supportedLocales`). There is no engine picker in normal Settings — only a hidden Labs toggle (see SettingsView note).

### Dictation pipeline & Intents
**Role.** The end-of-recording tail and the AppIntents entry points: after the mic stops, one shared pipeline classifies the utterance (fresh vs follow-up), publishes to clipboard, optionally persists a transcript, and drives the terminal pipeline-phase transition — identically across every entry point. (No Live Activity / Dynamic Island path exists — it was removed; see `DictationActivityCoordinator` in the blast radius.)
**Entry points.** `DictationPipeline.completeEndOfRecording`, `DictationIntentBridge.shared.controller`, `DictationController.stopAndTranscribe`, `DictateIntent.perform`, `RecordAndTranscribeIntent.perform`, `CaptureTextIntent.perform`.
**Invariants.**
- **Publish-first contract**: derive text, publish to clipboard FIRST, then append to ledger best-effort. A ledger/persistence throw must NEVER gate the publish; both branches degrade to publishing RAW transcript on any cleanup/persistence error.
- `transcriptReady` is posted BEFORE the SwiftData append + mirror write — it signals "published", not "persisted". Listeners needing latest rows must NOT key off it.
- **No code-path divergence**: every dictation entry intent + hero + in-app callers route their tail through `completeEndOfRecording`. `TranscribeAudioFileIntent` is the deliberate exception (composable Shortcuts step, `.result(value:)`, headless, no follow-up classification).
- `CaptureTextIntent` ("Save a Note", `App/Intents/CaptureTextIntent.swift`) is a second deliberate exception: a headless discoverable intent that appends a supplied text string directly via `TranscriptStore.append` — no recording, no follow-up classification — bypassing `completeEndOfRecording`. NOT in `JotAppShortcuts.appShortcuts` (Shortcuts-catalog only, no Siri auto-phrase). **An intent's `IntentDescription` must stay Siri-free** — the App Store rejects any intent description containing the word "Siri" with ITMS-90626 (build 155 was bounced for exactly this).
- `transient=true` (in-Jot keyboard stop): run the full publish + terminal-phase path but persist NOTHING (no row, no supersession, no stats). Since the decouple-root-view rearchitecture, `transient` ONLY gates save/no-save — it no longer forks the delivery path. The former in-process `FocusedFieldInsert` bridge is gone; an in-Jot stop delivers text through the exact same keyboard auto-paste flush (`flushPendingAutoPasteIfPossible`) as every other host, woken by the same `transcriptReady` post.
- Command branch ordering: `markSuperseded(priorID)` MUST run BEFORE `append(child)` — a cross-file contract with `TranscriptHistoryMirror`+SwiftData's `supersededAt == nil` predicate.
- Each intent owns its preamble (controller lookup, idempotency guard, snapshot `recordingStartedAt`) but must NOT drive the terminal phase transition itself — the pipeline owns it via `DictationActivityCoordinator`'s follow-up-window handoff.
- Both intents declare `static var supportedModes: IntentModes { .foreground(.immediate) }` — the iOS 26 replacement for the deprecated `openAppWhenRun`. `RecordAndTranscribeIntent` is the primary, registered intent (`isDiscoverable = true`, bound in `JotAppShortcuts.appShortcuts`); `DictateIntent` is a dormant fallback (`isDiscoverable = false`, not registered there). All metadata statics `static let`, type/perform non-public; both share phase via the same bridge.
- The session-token-guarded defer publishes `.failed` ONLY if `currentSessionID` still matches.
- Every recording-start site logs `RECORDING START FROM: <site>` — preserve these.
**Blast radius.** Downstream of `RecordingService`/`stopAndTranscribe`; upstream of `ClipboardHandoff`, `TranscriptStore`, `DictationActivityCoordinator` (now a follow-up-window + recording-start-timestamp coordinator only — defined in `App/Intents/DictateIntent.swift`, not a standalone file; the ActivityKit/JotWidget path is removed, see the `DictationActivityCoordinator` doc-comment in `App/Intents/DictateIntent.swift` — the "Dynamic Island ghost-pill fix" note), `DictationStats`, and the keyboard. Callers: the four Intents, RecordingHeroView, JotApp warm-resume, `RecordingPipelineDispatch`, PhoneSideWCSession. Changing publish/append ordering, the transient contract, or supersession ordering ripples into keyboard auto-paste correctness and history-mirror visibility.

### Keyboard extension
**Role.** A dictation-only custom keyboard (separate process, ~60 MB ceiling, no Apple-FM) that drives recording in the main app via Darwin notifications + App Group state, then inserts the finished transcript into the host field.
**Entry points.** `JotKeyboardViewController`, `KeyboardStreamingHub.shared`, `flushPendingAutoPasteIfPossible`, `decideMicTap`, `refreshPipelinePhaseStateAndSideEffects`, `deadAppWatchdogTask`, `StreamingStrip`, `CorrectionReviewStrip`.
**Invariants.**
- **60 MB ceiling**: MUST NOT link Apple FM or FluidAudio — runs NO inference. Rewrite/cleanup AND the live preview re-transcribe loop run in the main app; the keyboard bounces via deep link + Darwin notification and only MIRRORS state.
- **Live state flows through one process-lifetime hub.** `KeyboardStreamingHub.shared` (a `@MainActor @Observable` singleton) owns the SINGLE set of cross-process subscriptions (streaming partial/loading, pipeline phase, warm-hold nudge, history-mirror, correction-asks) AND the projected `KeyboardRecordingState` that every controller observes BY REFERENCE — so a transient/ghost controller renders the SAME live state as the visible one (this structurally fixed the blank-preview bug where per-controller state diverged). `StreamingStrip` renders the hub's `streamingPartialText` mirror + the `streamingLoadingVariantLabel` loading line; it never produces preview text. The text itself is a plain-text `TranscribingText` render (no per-word reveal).
- **Correction-review strip — two modes: post-paste teach AND pre-paste HOLD deck (ask-before-paste).** `CorrectionReviewStrip` reads per-session asks (`CorrectionBridge.readAsks`) and writes verdicts via `CorrectionBridge.enqueueVerdict`; the main app drains them (`CorrectionInbox`). It runs no gate/rescore. Pre-paste deck: when asks exist for the session, `flushPendingAutoPasteIfPossible` **GATES** — opens the deck and returns WITHOUT inserting/consuming (paste held). **All deck state is ONE `ActiveDeck` value on `KeyboardStreamingHub`** (session + monotonic generation + asks + answers/skips + phase `.reviewing`/`.resolved`/`.inserting`), NOT per-controller dictionaries or SwiftUI-local progress: those died with the controller/view while the pending paste lived on. Consequences to preserve: every strip/controller deck action carries the `AskDeckToken` it was rendered with and is fenced on mismatch; the strip's `index` is DERIVED from answers/skips, so a remount resumes at the first unanswered card and a record can never be answered twice; verdicts are enqueued ONCE as a deduplicated batch at resolution (the app's `CorrectionInbox` is first-event-wins, so tap-by-tap enqueueing diverged from a last-value-wins paste); the flush branches on the deck phase BEFORE `ClipboardHandoff.readFresh()`, so a deck outlasting the 30s freshness window still pastes; only the last-appeared controller (`hub.isActiveController`) may drive the insert; and the deck is MODAL for dictation (`decideMicTap` → `.noop("ask-deck-open")`, CTA disabled) because the three transports are single-slot. On resolve the owner's picks are applied to the captured baseline via the SHARED `PasteEditResolver` (producer-validated `baseEdit`/`altEdit` descriptors verified verbatim, case-SENSITIVE no-op test, overlapping batch rejected whole) and the same flush is **RE-ENTERED** so the one proven insert path runs once. Terminal cleanup (`hub.clearAskDeck(sessionID:)`) is session-scoped and runs on EVERY end: success, clipboard fallback, empty payload, terminal log, synthesized `.failed`, launch deadline, teardown-consume, unresponsive-app recovery, supersession, and a no-pending sweep. Requires asks to be STAGED BEFORE the clipboard handoff (`DictationPipeline` publishes asks data with `signalReady:false` ahead of `ClipboardHandoff.publish`; posts `correctionAsksReady` only AFTER the handoff so the legacy post-paste nudge can't precede the paste). "Stop asking" → a `suppress` verdict (`CorrectionInbox` → `CorrectionStore.suppressBlock`). Keyboard-only suppression: repeated keeps (`blockedKeeps≥2`) or suppress hide a pair from keyboard asks (`CorrectionAsksPublisher` filter) but NEVER from the transcript review.
- **Keyboard-active heartbeat.** While up, the keyboard writes `AppGroup.keyboardActiveHeartbeat` (~1s timer) so the main app (W6 globe cue) can infer the keyboard is on screen.
- Dictation-only by design (no QWERTY), surfaced in onboarding (W6).
- **Never open SwiftData**: Recents read ONLY from `TranscriptHistoryMirror` (App Group JSON).
- All typing goes through `textDocumentProxy` (safe without Full Access). Paste, mirror reads, and App Group writes require Full Access — guard every AppGroup path behind `hasFullAccess`.
- Reload recents on `historyMirrorUpdated`, NOT `transcriptReady` (publish-first means transcriptReady fires before the mirror write → stale recents).
- Height pin (`heightConstraint` 200pt, priority 999) MUST equal `KeyboardView`'s `.frame(minHeight:)` or controls clip off-screen.
- Auto-paste must not double-insert: gate with `isAutoPasteInsertInFlight` + `autoPasteAttempted` + payload session-ID match; after proxy re-sync, verify the insert LANDED before consuming the payload. For re-mounting web/custom host fields (Claude, Slack) that drop the IPC mid-record, `flushPendingAutoPasteIfPossible` does `adjustTextPosition(0)` then POLLS for a stable input session (two consecutive equal context reads) before inserting, and corroborates success via the host `textDidChange` callback + a deferred settled re-read — the reliability fix for paste failing into web fields. The deferred re-read treats a NIL settled context (`settledLen == -1`, proxy disconnected after the host re-rendered — common on the ask-before-paste re-entry into web fields) as INCONCLUSIVE, not a revert (a genuine revert leaves a shorter but non-nil context); when the immediate post-insert read confirmed the insert it's trusted, so a disconnect no longer false-flags "couldn't paste".
- The keyboard can't detect a jetsammed app directly; arm `deadAppWatchdogTask` (5s) on each control tap and tombstone the frozen `.recording` session (`recoveredZombieFreeze`).
- Foreground routing (warm-vs-cold, inline-vs-cold) is decided from a single `AppGroup.isJotAppForeground()` read plus the unified `RecordingRecord`/`PipelinePhaseProjection`'s `liveness` field — no cross-process round-trip. The old `keyboardForegroundPing`/`appForegroundPong` handshake was removed in the B4 cleanup.
- Don't mirror `hasFullAccess` to the App Group — iOS gates App Group writes itself; a mirror can't be trusted.
**Blast radius.** Couples to the main app entirely through `Shared/` infra: `CrossProcessNotification` (stop/pause/resume/cancel, ping/pong, pipelinePhaseChanged, historyMirrorUpdated, warmHoldNudgeChanged, streaming partial/loading, correctionAsksReady), `PipelinePhaseProjection`, `TranscriptHistoryMirror`, `ClipboardHandoff`, `CorrectionBridge`, AppGroup keys (incl. `keyboardActiveHeartbeat` written back). App-side responders: `HomeScreen.updateDictateTapObserver`, RecordingService, DictationPipeline, PreviewScheduler (preview projection), CorrectionAsksPublisher/CorrectionInbox, SetupWizardView W6, WarmHoldNudgeView. Changing Darwin names, AppGroup keys, or the projection/mirror schema breaks the contract on both sides.

### Cross-process plumbing
**Role.** The shared App-Group state layer (UserDefaults keys, Darwin notifications, JSON projections/mirrors) that lets the app, keyboard, and watch observe and hand off dictation state without sharing a process or opening SwiftData.
**Entry points.** `AppGroup.defaults`, `CrossProcessNotification.post`, `PipelinePhaseProjection.write`, `ClipboardHandoff.publish`, `TranscriptHistoryMirror.refresh`.
**Invariants.**
- The App Group ID must be listed under `application-groups` for every PROCESS that touches shared state — the **main app, the keyboard, and the share extension** (the three targets wired to entitlements files in `project.yml`) — or `AppGroup.defaults` fatalErrors and `containerURL` returns nil. The watch app/widgets (WCSession, not App Group) and the unit-test bundle correctly carry no App Group; don't try to enforce it on them.
- **Membership trap — verify from project.yml, not the entitlements files.** `Resources/Watch.entitlements` and `Resources/WatchWidgets.entitlements` DO exist and DO list the App Group, but they are ORPHAN files: in `project.yml` only the `Jot`, `JotKeyboard`, and `JotShareExtension` targets carry an `entitlements:` key — the `JotWatch`/`JotWatchWidgets` target blocks have none (their comments note "No entitlements file"), so the watch app/widgets build WITHOUT the App Group regardless of those on-disk files. Confirm membership from each target's `entitlements:` key in `project.yml`, NOT from `grep -rl application-groups Resources/*.entitlements` (which falsely returns all four). The two watch/widget files remain orphan deletion candidates; `Resources/ShareExtension.entitlements` is NOT an orphan — it's legitimately wired via `JotShareExtension`'s `entitlements:` key.
- **Darwin notifications are signals only, never truth**: a notification just tells a reader to RE-READ the projection. Correctness comes from projection state + `lastUpdatedAt` heartbeat.
- UserDefaults is atomic per-key but NOT across keys — any multi-field handoff must be one JSON blob under one key (`ClipboardHandoff.FreshDictation`, `PendingPasteSession`) so the keyboard can't observe a torn write.
- **Writer/reader roles are fixed**: the MAIN APP writes projections; the KEYBOARD only reads. `read()` may synthesize a `.failed` view in-memory for a stale heartbeat but never writes it back.
- The keyboard NEVER opens a ModelContainer — reads history via `TranscriptHistoryMirror.load()` (pure JSON). `+SwiftData.refresh(from:)` compiles into the keyboard but must only ever be invoked from main-app paths.
- ~60 MB ceiling ⇒ projection values are pre-resolved primitives (e.g. `streamingLoadingVariantLabel` stores a display string, not the enum).
- Each projection carries its own staleness window and they are deliberately different — do not unify. The exact thresholds live as constants beside each projection type.
- `AmplitudeProjection` encodes its timestamp as milliseconds-Double, NOT iso8601 (ISO8601 truncates subsecond precision). Don't "normalize" it.
- Default-ON vs default-OFF is encoded per accessor (e.g. `warmHoldEnabled`: missing ⇒ false). Reusing the wrong pattern flips a default.
- The `speechModelVariant` getter always returns `"english"` on read (single bundled model) — every legacy/unknown value resolves to it. The retired `aiRewriteProvider` / `askBackend` / `embeddingsEnabled` keys are removed from defaults at launch (`JotApp.init`).
- Cross-process shared state the keyboard reads is not just the projection families (ClipboardHandoff / PendingPasteSession / PipelinePhase / Amplitude / TranscriptHistoryMirror): the rewrite/cleanup config keys are also App-Group contracts — `rewriteMode` (engine choice), `lastDictationStatusMessage` (keyboard banner) plus `cleanupEnabled`/`cleanupPromptID`/`cleanupPasteCleaned`/`cleanupInstructions` (Automatic cleanup config, `CleanupSettings` — NOTE `cleanupEnabled` is written by BOTH sides: the app's AI settings card and the keyboard's Cleanup tile, `JotKeyboardViewController.handleCleanupToggle`) and `aiCleanupAvailable` (app → keyboard mirror of `RewriteClient.isAvailable`, refreshed on every foreground via `RewriteClient.mirrorAvailabilityToAppGroup`, so the keyboard can refuse to switch on a cleanup Apple Intelligence can't run); the former `AppGroup+Rewrite` job/result slots went with the Qwen keyboard handoff. The streaming/preview + correction families join this inventory: `streamingPartialText` (preview mirror), `streamingLoadingVariantLabel`/`streamingLoadStartedAt` (loading line), `wizardActive` (koan gate), `keyboardActiveHeartbeat` (keyboard→app liveness), `transcriptionLanguage` (`jot.transcription.language` — the dictation-LANGUAGE source of truth, a plain string read in `Shared` so keyboard/watch resolve it WITHOUT linking FluidAudio; defaults to `"english"` when missing), and the `CorrectionBridge` `jot.correction.asks`/`jot.correction.verdicts` blobs. Treat all of these as part of the App-Group key inventory. (The `previewSource` engine-select key was removed with the EOU rip.)
- **The keyboard→main-app write-back exceptions.** Readers are normally read-only, but THREE keyboard writes back are sanctioned: the warm-hold terminal actions, the correction `enqueueVerdict`, and `keyboardActiveHeartbeat`. Each is a bounded, well-defined slot — not a general license for the keyboard to author projections.
**Blast radius.** Written by main-app dictation (RecordingService, DictationPipeline, PreviewScheduler/StreamingPartial, CorrectionAsksPublisher, JotApp, TranscriptStore); read by the keyboard + watch bridge, with the keyboard writing back the three sanctioned slots (warm-hold actions, `CorrectionBridge.enqueueVerdict`, `keyboardActiveHeartbeat`). Adding a cross-process feature almost always means a new `AppGroup.Keys` entry + a `CrossProcessNotification.Name` + (often) a projection struct; changing a key name silently desyncs whichever process wasn't recompiled in lockstep.

### SwiftData schema & store
**Role.** On-device transcript persistence: the frozen versioned schema (`@Model` shapes), its Flyway-style migration plan, and the singleton ModelContainer + typed store wrappers every read/write goes through.
**Entry points.** `JotModelContainer.shared`, `JotMigrationPlan.stages`, `JotSchemaV9`, `TranscriptStore.append`, `typealias Transcript`.
**Invariants.**
- **FROZEN RULE**: once a `JotSchemaVN.swift` ships, never edit it. Add a field by copying to `V(N+1)`, appending a `MigrationStage`, and bumping the `Transcript` typealias + `Schema(versionedSchema:)`. `scripts/check-schema-frozen.sh` blocks PRs touching a non-max VN.
- Every new VN MUST bump `versionIdentifier` or SwiftData can't distinguish versions and corrupts the store.
- Additive fields use `.lightweight`; renames/removes/type-changes require `.custom`. All 8 shipped stages (V1→V9) are lightweight. V8 added `Transcript.language: String?` (the dictation language; nil ⇒ treat as English) for the language badge + language-aware Translate/re-transcribe; V9 added `Transcript.diarizationJSON: String?` (the persisted `[PersistedSpeakerRow]` for Speaker Notes).
- **Watch-target schema enumeration gotcha.** The `Shared/` glob compiles every `JotSchemaVN.swift` into the `Jot`/`JotKeyboard` targets automatically, BUT the `JotWatch` target lists each schema file EXPLICITLY in its `project.yml` `sources:` (not a glob). Every new `JotSchemaVN.swift` must be added to that list by hand or the watch build breaks. (See also the cross-process invariant in Bird's-eye view.)
- `JotModelContainer`/`TranscriptStore` are MAIN-APP-ONLY (`#if JOT_APP_HOST`); the keyboard reads via `TranscriptHistoryMirror` JSON only. Source location in `Shared/` does not relax this — it's a runtime invariant.
- Store lives in the App Group container (`groupContainer: .identifier`), name `JotTranscripts`, `cloudKitDatabase: .none`.
- `JotModelContainer.shared` is a `@MainActor` singleton (not the scene modifier) because headless intents append without foregrounding. `ModelContext` is not Sendable — fresh context per call on `@MainActor`.
- If versioned init fails, a fallback constructs a non-versioned container, logs `[SCHEMA-FALLBACK]`, sets `jot.schema.fallbackActiveSince_v1`. Watch Console for it on real-device upgrade tests.
- `category` is DEAD-DATA from V6; `TranscriptCategory` DORMANT, `TranscriptEmbedding` DEPRECATED — retained so V6→V7 stays additive.
- `ledgerIndex` comes from `jot.ledger.nextIndex` (survives deletes ⇒ stable `#NNNN`; per-device, not synced).
- `TranscriptChunk.createdAt/durationSeconds/source` are denormalized copies of the parent, stamped at index time — keep in sync.
- Transcript↔Embedding/Category/Chunk joins are LOGICAL (via `transcriptID` UUID), NOT `@Relationship` — derived rows are rebuildable. All three derived entities are now DORMANT (the embedding pipeline is gone; retrieval is Core Spotlight) but stay in the frozen schema until a `.custom` migration drops them.
- After creating a new VN file, run `xcodegen` from `Jot/` so the `Shared/` glob compiles it into both targets.
**Blast radius.** `TranscriptStore` is the single write path; every mutation fans out `TranscriptHistoryMirror.refresh`, `historyMirrorUpdated`, and a `TranscriptSpotlightIndex.index/.delete` projection update. Readers: ContentView, EditPromptWithTestSheet, AskPipeline/TranscriptSpotlightIndex, PhoneSideWCSession. Any `@Model` change ripples to the migration plan, the frozen-check script, the typealias, both init paths, and `docs/schema-migrations.md`.

### Ask (Private Cloud Compute + Spotlight)
**Role.** Question-answering over the user's transcript library and Jot's built-in help. On iOS 27 the model is Apple's `PrivateCloudComputeLanguageModel` (usable only once `PrivateCloudComputeAccess.isEntitled` — see the AI Rewrite invariants); retrieval is Apple's `SpotlightSearchTool` over the Core Spotlight projection of every note (`TranscriptSpotlightIndex`) plus `JotHelpSearchTool` (BM25 over the bundled help corpus). No embedder, no vector store, no download. Below iOS 27 Ask is unavailable and its entry point is hidden.
**Entry points.** `AskPipeline.run`, `AskController.ask/.availability/.isAvailable`, `AskEngine.answer`, `TranscriptSpotlightIndex.index/.delete/.reindexAllIfNeeded`, `JotHelpSearchTool`, `HelpCorpusIndex.retrieve`.
**Invariants.**
- **One pipeline, two deliveries.** `AskPipeline.run` is the only place that builds a session; `AskController` mirrors its `onSources`/`onPartial` callbacks into `@Observable` state, `AskEngine` (Siri/Shortcuts) ignores them and returns the final `Outcome`. Never fork retrieval or prompts between the two.
- **Two question shapes.** A pure date window with no topic (`parseDateScope` + `!queryHasTopicBeyondDate`) is answered from a local chronological fetch (`retrieveByDate`) with the numbered `[cite: N]` contract (`AskCitationParser`); everything else is tool-driven — the model calls the Spotlight tool itself, and the notes it retrieved (mirrored from `SpotlightSearchTool.searchResults`) become the sources. Tool-shape answers carry no numbered citations.
- **The Spotlight index is a projection, never truth.** `TranscriptStore` is the only writer; `TranscriptSpotlightIndex.indexVersion` bumps force a full re-projection at launch; Spotlight's own reindex requests route through `CSSearchableIndex.default().indexDelegate` (set in `JotApp`). Items never expire (`expirationDate = .distantFuture`) and carry `displayText` as `textContent`; `uniqueIdentifier` is the transcript UUID string, which is how tool results map back to `Transcript` rows (`fetchTranscripts(ids:)`).
- **Availability is one rule** (`AskController.availability()`): iOS 27 ∧ `PrivateCloudComputeLanguageModel().availability == .available` ∧ `!quotaUsage.isLimitReached`. `UnavailableReason` cases map to user copy in `AskView` and to spoken lines in `AskJotIntent`.
- Private Cloud Compute errors (`networkFailure` / `quotaLimitReached` / `serviceUnavailable`) are translated to user copy in `AskPipeline.describe`; nothing raw reaches the UI.
- All Ask files are `#if JOT_APP_HOST` — app-target only, never the keyboard. `HelpCorpusIndex` is text-only (no `modelVersion`); `scripts/check-help-corpus-fresh.sh` still guards `sourceHash` vs `features.md`.
- `AskJotIntent` is registered in `JotAppShortcuts.appShortcuts` with one `"Ask <app>"` phrase — the iOS-26.2 daemon-commit binding caveat applies, so the whole provider, incl. the Action-Button tile, must be re-verified after touching it.
**Blast radius.** Reads the Transcript store (through `TranscriptSpotlightIndex` and `retrieveByDate`). Depends on FoundationModels (Private Cloud Compute), CoreSpotlight and `_CoreSpotlight_FoundationModels` (the tool). Spotlight deep links (`CSSearchableItemActionType`) enter through `JotApp` and reuse the keyboard's open-transcript router.

### Transcript Detail & Editing
**Role.** The full-screen detail surface for a saved transcript: Original/Rewrite tab segment, metadata subline, selectable text, the bottom action bar (Delete / Edit / Rewrite / Translate / Copy), rewrite progress+cancel, rewrite feedback, and in-place editing of either tab — including dictating straight into the field being edited, Proofread (iOS 27), and the edit bar's AI button that rewrites the draft in place with the Cleanup prompt. A keyboard recents-row arrival (`openInRewrite`, from `KeyboardRewriteRouter`'s `autoRewrite` flag) runs the Cleanup prompt onto the Rewrite tab on appear (or just shows the tab when a rewrite exists); there is no read-only Writing Tools selection mode any more.
**Entry points.** `TranscriptDetailView` (tab segment + action bar), `InlineEditTextView`, keyboard auto-paste (in-field dictation insert path — see Dictation pipeline & Intents).
**Invariants.**
- Edit fate differs by tab and is load-bearing (see features.md §3.7 / §13.5): Original-tab edits OVERWRITE in place (no retained original); Rewrite-tab edits preserve the model output as the training-pair "before". Never collapse these two paths into one.
- `InlineEditTextView` assumes every edit it can produce (type / backspace / paste / select-replace / dictation insert-on-stop) is a **SINGLE CONTIGUOUS replacement**, and recovers the changed range by common-prefix/common-suffix delta in UTF-16 space — deliberately NO LCS/fuzzy diffing (which would mis-mark repeated dictation words) and NO multi-range edits. Adding either requires revisiting this delta logic.
- The italic "changed this session" styling is a session-only cue: the bound `text` is always plain `String`, so Save is flatten-on-save (no styling persisted); `sessionToken` re-baselines the whole text as "original".
- In-field dictation flows through the SAME `InlineEditTextView` delta path and persists no separate transcript (cursor-insert / Cancel-Save-disabled behaviour is features.md §3.7).
**Blast radius.** Reads/writes the Transcript store for in-place edits; the Articulate action drives the AI Rewrite & LLM subsystem (in-app rewrite trigger, routes to AI Rewrite settings as a sheet when the model isn't ready); the rewrite-edit "before/after" pair feeds §13.5 training data. Shares the keyboard auto-paste flush with the dictation insert path. Changing the single-contiguous-replacement assumption or the Original-vs-Rewrite edit fate ripples into the changed-range cue, the dictation-insert path, and the training-pair contract.

### AI Rewrite, Cleanup & Proofread
**Role.** Text transformation on Apple Foundation Models: the user's SavedPrompts drive `RewriteClient` (on-device `SystemLanguageModel` with `@Generable Rewrite` guided generation; on iOS 27 a prompt that won't fit the on-device `contextSize` — or an on-device failure — falls back to `PrivateCloudComputeLanguageModel`); `CleanupService` drives cleanup + chained-command resolution on the on-device model; `GrammarCheckService` (iOS 27, `UITextChecker.requestGrammarChecking`) is the model-free proofread behind the editor's Proofread button. **There is ONE engine.** The `RewriteMode` fork (Jot's prompts vs system Writing Tools), `AppleIntelligenceRewriteGuide`, the detail's read-only selection mode and the "Tap the selection, then ✎ Writing Tools" hint were removed 2026-09-15: every AI affordance — the detail sparkle, the edit-bar AI button, the keyboard recents-row arrival (`autoRewrite`) and the keyboard's own Rewrite tile — runs a saved prompt itself. Nothing in Jot points the user at the system Writing Tools menu (iOS still offers it on any selected text; Jot doesn't depend on it).
**Entry points.** `RewriteClient.shared.rewrite`, `RewriteClient.availability`, `CleanupService.clean/.resolveUtterance`, `GrammarCheckService.check/.apply`, `SavedPromptStore.all`, `LegacyModelPurge.runAllIfNeeded`.
**Invariants.**
- **No Jot-owned model, no download, no weights.** Everything runs through FoundationModels sessions; `LegacyModelPurge` deletes the retired Qwen/Phi-4 HF-cache snapshots and the EmbeddingGemma CoreMLLLM tree once per install.
- Instructions are trusted, the transcript is not: the prompt goes in `instructions`, the user's text in the user turn — and the text is quoted as DATA. `Shared/LLM/RewriteInstructions.swift` is the one framing for `RewriteClient`, `KeyboardRewriter` and `CleanupService.clean`: the instructions say the quoted text is never a message to the model (a dictated question must come back as a question), the user turn is `RewriteInstructions.userTurn` (`<<< … >>>`). No output heuristics or retries (owner rule 2026-09-17: a second model pass doubles the wait; if the framing fails, that is what pastes). The framing is MEASURED, not guessed: `scripts/rewrite-probe/run.sh` runs the real on-device model on the Mac with the actual instructions + the built-in Cleanup prompt over 24 dictated questions/requests and prints the outputs — run it before touching the framing or a default prompt (2026-09-17 baseline: old framing answered 8 of 20; current framing 22 of 24 clean, misses: "draft a reply saying no thanks" → a refusal-like line, "list the pros and cons of moving to friday" → a heading). Apple's docs: the model obeys instructions over prompt content. `CleanupService.resolveUtterance` (chained follow-up commands) is deliberately NOT framed this way — there the utterance IS the instruction.
- Route order in `RewriteClient.rewrite` is on-device → Private Cloud Compute, never the reverse; the iOS 27 `tokenCount(for:)`/`contextSize` budget decides up front, so long transcripts never fail on-device first. `RewriteClient.wouldUsePrivateCloudCompute` is what the settings strip / footer read to stay honest.
- **Private Cloud Compute is gated by `PrivateCloudComputeAccess.isEntitled`, not by the framework.** Apple's PCC is a managed entitlement (Small Business Program + <2M downloads, requested at developer.apple.com/private-cloud-compute/); without it `PrivateCloudComputeLanguageModel().availability` STILL reports `.available` on an eligible iOS 27 device and every request fails with `ModelManagerError 1046` (verified on macOS 27 with an unentitled probe, 2026-09-14). So `RewriteClient.cloudIsUsable` and `AskController.availability()` check the flag first; Ask stays hidden (`.awaitingAccess`) and rewrites never fall back to the cloud until the entitlement is granted, added to `Resources/Jot.entitlements`, and the flag flipped in the same change.
- **The background rate limit is handled by deferral, never by retrying.** Apple's Foundation Models documentation: rate limiting "will only happen if your app is running in the background and exceeds the system defined rate limit" — exactly the keyboard-dictation cleanup path (the app is backgrounded, alive for the mic). `RewriteClient` maps `LanguageModelError.rateLimited` (iOS 27) / `GenerationError.rateLimited` (iOS 26) to `Failure.rateLimited(resetDate:)` (`RewriteClient.isRateLimited(_:)` is the caller-side test) and never retries; while `cloudIsUsable` is false the two iOS 27 `tokenCount(for:)` budgeting calls are skipped (they buy nothing without a cloud route and spend the same limit). `DictationPipeline` reacts by pasting the raw words and enqueuing the transcript id in `DeferredCleanupQueue` (Application Support JSON, main app only); ContentView's scene-active hook drains it on the next foreground — `RewriteClient.rewrite` → `TranscriptStore.setCleanedText` + `RewriteProvenance.record(automatic: true)`, bracketed by `CleanupActivity` so the home row / note show "Cleaning up". The keyboard status row for the deferred case reads "Pasted as spoken — cleanup will finish when you open Jot". Every failed rewrite is a `DiagnosticsLog` `.rewriteFailed` entry (metadata `rateLimited`, `error`); the deferral pair is `.cleanupDeferred` / `.cleanupDeferredRan`, and `DiagnosticsView.diagnosticsChipMetadata` labels all three (its switch is exhaustive on purpose — a new category is a compile error there).
- **Rewrite provenance is a sidecar, not schema.** `RewriteProvenance` (Application Support `RewriteProvenance.json`, keyed by transcript UUID: prompt name + automatic flag + landed-at) is written by `DictationPipeline` (automatic cleanup, both modes) and `TranscriptDetailView.startRewrite` (manual), and removed inside `TranscriptStore.discardRewrite/.delete` so no caller can leak a stale record. `CleanupActivity` (in-memory `@Observable`) is the "background cleanup still running for note X" signal the home rows and the detail read — the pipeline's `attachCleanup` brackets it.
- **The keyboard may run the on-device model, never the cloud.** `Keyboard/KeyboardRewriter.swift` (actions pane Rewrite tile, §7.15) calls `SystemLanguageModel` directly from the extension — inference is out-of-process, so the 60 MB ceiling is unaffected — with the same instructions/user-turn split and `@Generable Rewrite` as `RewriteClient`, a 20 s cap, and a cancel on `viewWillDisappear`. The replacement is applied by typing over the selection (`textDocumentProxy.insertText`) after re-checking `selectedText` is unchanged, and is recorded as `KeyboardUndoLedger.replacement` so Undo reverses it. `PrivateCloudComputeLanguageModel` must never be touched from the keyboard.
- **Keyboard translation is installed-packs only.** `Keyboard/KeyboardTranslator.swift` (Translate tile, §7.16) uses `TranslationSession(installedSource:target:)` — the framework's non-SwiftUI session, valid only when the pack is on the phone (`LanguageAvailability.status == .installed`, checked per target when the pane opens). Downloads need the app's `.translationTask` host (`TranslationGateway` / `TranslationTaskHost` in `TranscriptDetailView`), so the keyboard never triggers one; it dims the chip and points at §3.9. Source language = `NLLanguageRecognizer` on the selection. Language list is shared: `Shared/TranslationLanguages.swift` (app sheet + keyboard). Last target: `AppGroup.Keys.keyboardTranslateTarget`.
- **Keyboard status is a row inside the surface, never an overlay.** `Keyboard/KeyboardStatusRow.swift` (`KeyboardStatus` = message + derived severity + hold duration; `KeyboardStatusRow` = the tinted row, tap-to-dismiss, self-timed leave) is hosted by `RecentsStrip` (dictation outcomes, between header and rows — the rows pane gives up its height because the keyboard's height is fixed) and `ActionsPopover` (rewrite/translate outcomes, above the tiles). `KeyboardView` only derives `keyboardStatus` from the controller's `statusBanner`; dismissal = `onStatusBannerRendered` → `clearStatusBannerSlot` (App Group `lastDictationStatusMessage` + controller state). The old `.overlay(alignment: .top)` banner is gone; a status that arrives while the streaming strip is up shows when Recents returns. Toggles (Cleanup) set no status at all (§5.6 / §5.10).
- **The post-stop stage word is derived, not published.** `.processing`/`.publishing` are internal beats; `RecordingService.lastNamedPipelineStage` (app) and `KeyboardRecordingState.lastNamedStage` (keyboard, from the same projection) each hold the last of `.transcribing/.cleaning/.rewriting` so every surface (hero stop capsule, home return pill, keyboard pill + strip header) shows "Transcribing / Cleaning up / Rewriting" and never a generic "Working" — no new App-Group key. The keyboard keeps `StreamingStrip` mounted while `isInflightPostRecording` (`isFinishing`), so the live text is held still instead of dropping to the recents strip mid-wait.
- **One engine, no picker.** `RewriteMode` is gone (a stale `jot.ai.rewriteMode` App-Group value is ignored). Every rewrite requires Apple Intelligence; there is no fallback engine — an unavailable engine routes to the AI settings sheet (detail, edit bar, recents-row arrival) or explains in the keyboard banner (keyboard tiles).
- Cleanup config is App-Group-backed (`CleanupSettings` reads/writes `AppGroup.Keys.cleanupEnabled`/`cleanupInstructions`) and is therefore a cross-process main-app↔keyboard contract. `FollowUpDiscoveryState`, by contrast, is `UserDefaults.standard` (NOT the App Group) — main-app-local.
- The keyboard's recents-row Rewrite button opens the note in the main app and has the app run the rewrite: `jot://transcript?id=…&ai=1` → `KeyboardRewriteRouter.setPendingOpenTranscript(id:autoRewrite:)` → `TranscriptDetailView(openInRewrite:)` runs the Cleanup prompt on arrival. The old `jot://rewrite` job/result handoff is gone. (The keyboard's own in-place Rewrite tile is the FoundationModels bullet above — that is the one case the keyboard runs inference itself.)
- **Automatic cleanup (§7.14) has two routes in `DictationPipeline.completeEndOfRecording`**: `pasteCleanedText == true` waits in the `.cleaning` phase and publishes the cleaned text (the pre-existing `cleanupEnabled` path, now through `RewriteClient`); `false` publishes raw immediately and `cleanUpInBackground` attaches the result via `TranscriptStore.setCleanedText` after the append. Transient (in-Jot) stops never clean in the background (no row to attach to); the command branch never runs it (its single round-trip already cleaned). `CleanupSettings.load()` resolves the prompt text at call time (chosen prompt → built-in Cleanup → legacy text).
- Proofread never applies silently: `GrammarIssue`s are underlines (`InlineEditTextView.highlightRanges`) + an accept/ignore sheet; any `editorText` change clears them because offsets go stale; accepting re-runs the check.
- SavedPrompt defaults have hardcoded stable UUIDs; `DefaultKind` keys on them so a rename keeps its kind. `seedIfNeeded()` only seeds an EMPTY list; the Articulate/AI-prompt migrators run unconditionally every launch (pre-launch, no flag).
- `SavedPromptStore` is App-Group-UserDefaults backed; `all()` never auto-seeds; `save()` normalizes `sortOrder` to `0..<count`.
**Blast radius.** Driven from TranscriptDetailView (Rewrite pill, voice prompt, Proofread), the prompt sheets, AIRewriteSettingsView, and the dictation pipeline (`CleanupService.resolveUtterance`/`ChainedFollowUp`). ### Apple Watch & Connectivity
**Role.** A standalone watchOS app that records audio locally, queues it, and transfers it to the paired iPhone over WCSession for on-device transcription, while receiving the iPhone's top-10 list back for a read-only recent view.
**Entry points.** `PhoneSideWCSession`, `WatchConnectivityClient`, `WatchSyncQueue`, `WatchRecorder`, `WatchTranscriptStore`.
**Invariants.**
- WCSession messages are an untyped string-keyed protocol with `schemaVersion:1` — watch sends `file` + `helloFresh`; phone sends `topTranscripts`/`ack`/`transcribing` (all `transferUserInfo`, FIFO + guaranteed delivery). Add new types to BOTH switch statements; `dict[key] as? T` silently parses an Any-wrapped Optional as nil — encode `source` as String or omit.
- **Watch dictation language.** `WatchLanguage` (`Shared/WatchLanguage.swift`) is a Foundation-only MIRROR of the app's `LanguageChoice` — the watch target can't link FluidAudio, so it re-declares the language set with NO script-hint dependency. Invariant: its `rawValue`s must stay BYTE-IDENTICAL to `LanguageChoice` so codes round-trip (`WatchLanguage.code` → `LanguageChoice.fromStored`); keep both lists in sync. The picker (`WatchLanguagePickerView`, Digital Crown) persists to `WatchLanguageStore` and rides WCSession two ways — per-file `language` metadata on the audio transfer (`WatchSyncQueue.PendingFile.languageCode`) AND a standalone `languageSelection` userInfo. Phone-side `PhoneSideWCSession.applyWatchLanguage` adopts it into `AppGroup.transcriptionLanguage` but is **change-gated** (no-ops when already that language, and never auto-downloads a not-yet-present European model from an unattended message).
- In `session(_:didReceive:)` the file MUST be copied to staging SYNCHRONOUSLY (`stageFileSync`) before the delegate returns — iOS reclaims `file.fileURL` the instant it returns. Never move the copy into the async hop.
- A received audio UUID is added to `recentlyReceivedUUIDs` ONLY after transcribe+save succeeds — early-marking poisons the retry path.
- The sync queue is fail-closed at 50 pending (`maxPendingCount`) — new captures BLOCKED with an alert, never drop-oldest; cap enforced at the UI layer, but `enqueue()` itself always accepts to avoid losing captured audio mid-race.
- Watch audio is AAC 16kHz mono to match Parakeet (no resampling on phone). Capture `currentTime`/`duration` BEFORE `recorder.stop()`.
- Recording uses `WKExtendedRuntimeSession(.audioRecording)`; on invalidation DO NOT call `recorder.stop()` (truncates the m4a). `stopAndSave` has a disk-recovery fallback scanning `Pending/`.
- Recording sheet (2026 redesign): tapping the coral hero stops + saves; the timer lives inside the circle, no "Stop" word. On watchOS 26 `interactiveDismissDisabled(true)` does NOT suppress the system sheet ✕ (verified on-sim) — so `RecordingView.cleanup()` SAVES on any dismiss-while-recording (capturing `WatchRecorder.shared`/`WatchSyncQueue.shared` directly in the teardown Task), never `cancelIfActive()` (discard). "Never lose audio" holds for every exit.
- `WatchTranscriptStore` is READ-ONLY on the watch; all editing is on the phone. Phone re-pushes top-10 on every library change via `historyMirrorUpdated` (250ms debounced).
- Watch-originated transcripts save with `source='watch'` + `watchOriginUUID`; SwiftData dedup keys on it. The save path MUST mirror `TranscriptStore.append` (refresh mirror + post + index).
- Phone/watch acks are independently deduped, both bounded to 100, oldest-first. `resetSync()` re-activation is the documented WCSession-daemon-stall workaround.
- The `transcribing` placeholder store is keyed by AUDIO FILE UUID (cleared by the ack), NOT by `topTranscripts`'s `transcript.id`. The two UUID spaces never match.
- **Watch pending UI is driven by `WatchSyncQueue` ONLY** (`WatchPending.waitingToSync`), never `WatchPendingTranscribingStore`. The queue is file-backed + self-cleaning (an entry exists iff an unacked `.m4a` is on disk; the ack deletes it). The transcribing placeholder's sole clear signal is the app-level ack, so it orphans permanently on any transcribe failure / lost / out-of-order ack — the "stuck Transcribing… forever" bug. The store still exists + is populated (harmless), just not rendered. "Waiting to sync" cards offer **tap-to-play** (`WatchPendingAudioPlayer`, `.playback` session on the local `.m4a`) and **swipe-to-delete** (`WatchSyncQueue.remove(uuid:)` — user discard, distinct from `ack`).
**Blast radius.** Activated phone-side from `JotApp` (`PhoneSideWCSession.shared.activate()`). Writes into the shared SwiftData store (`source='watch'`), so it depends on the schema/migration system and feeds Home, keyboard Recents (mirror + notification), Ask indexing, and TranscriptionService. Watch app + widgets are separate watchOS targets. Deep-link `jot-watch://record` launches RootView into recording. Diagnostics surface on-watch (`DiagnosticsView`) and on-phone (`DiagnosticsWatchView`).

### Warm Hold
**Role.** Keeps the audio session alive for a configurable cooldown after a recording stops so the next keyboard dictation starts instantly — while yielding the mic to any other app that needs it during the window — and, via a cross-process streak-detection nudge, invites app-bouncing users to enable it.
**Entry points.** `enterWarmHold`, `exitWarmHold`/`releaseWarmHold`, `detectWarmHoldSwitchingNudge`, `qualifyingReturnStreak`, `handleMicCTATap`.
**Invariants.**
- Two independent axes: "end the transcription" and "release the mic / warm-hold" are SEPARATE. Warm hold is orthogonal to dictation routing and must NOT change WHERE a dictation goes.
- Warm hold is ONLY a start-faster optimisation. A keyboard Dictate tap inside the warm window while Jot is FOREGROUND must route inline (insert at cursor, no save); only when Jot is NOT foreground does `handleMicCTATap` take the warm-resume background-capture path. (Taking warm-resume while foreground was the "in-app dictation wrongly saved" root cause.)
- Never forceStop/discard to release a warm-held mic; use `exitWarmHold()`/`releaseWarmHold()`.
- Liveness is read from the unified `PipelinePhaseProjection`: warm hold is live when the phase is `.warmIdle`, `warmExpiresAt` is in the future, AND the projection's single `liveness` stamp is fresh. A stale/absent record ⇒ treat as no warm hold and fall through to cold-launch URL.
- The keyboard CANNOT run the streak math. The APP owns it: appends to `captureStopRing`, computes `qualifyingReturnStreak`, sets the `warmHoldNudgeShouldShow` boolean, posts `warmHoldNudgeChanged`. Keyboard/hero render off the boolean and write back only the two terminal actions.
- Streak detection fires after several consecutive qualifying returns inside a bounded window (thresholds are constants in `RecordingService`); the ring is capped. `detectWarmHoldSwitchingNudge` is called ONLY from the clean `stop()` site and dedupes on sessionID.
- The nudge is an OFF-state affordance: never show when `warmHoldEnabled` or `warmHoldNudgeSuppressed`. Passive ignore (~6s auto-hide) ≠ permanent suppression.
- Auto-hide is owned by the APP side only; the keyboard strip has no timer.
- `enterWarmHold` snapshots the duration ONCE at entry; later Settings changes must not resize an in-flight window. If a pipeline is in flight, publication defers (`pendingWarmHoldPublish`).
- Warm hold is mutually exclusive with Pause; `exitWarmHold` clears pause state defensively.
- **Mic-yield (production default, no toggle):** during the idle warm window `makeWarmIdleSessionMixable()` switches the session to `.playAndRecord` + `.mixWithOthers`, so ordinary other-app playback (YouTube, Reddit, Music) COEXISTS with a warm-held Jot instead of being blocked — the reverse of the original V1 design, shipped 2026-07-04 (see the Diarization/Voice-Clone-era "Warm hold: mixable idle session" commit). Only a genuinely hard interruption (a call, alarm, Siri, or another app grabbing an exclusive `.record` session) still reaches `handleInterruption(.began)` while warm → `exitWarmHold()` hands the route back (`setActive(false, .notifyOthersOnDeactivation)`). `startFromWarmHold` switches back to exclusive `.record` before resuming capture; restore failure → teardown + `RecordingError.warmYieldRestoreFailed` → cold `configureSession`. The V0–V5 experiment scaffolding, its hidden Settings stepper, and the in-app warm-yield diagnostics category were removed when V1 graduated to the unconditional default; V1's polarity was later flipped to mixable as described above.
**Blast radius.** Producer is RecordingService (+ the JotApp foreground heartbeat for host-detection). Consumers: `JotKeyboardViewController.handleMicCTATap` (+ nudge observer), KeyboardView/WarmHoldNudgeStrip, ContentView/WarmHoldNudgeView. State flows through `jot.warmHold.*` keys + two Darwin posts (`warmResumeRequested`, `warmHoldNudgeChanged`). `AskView.releaseWarmHold` gently exits on sheet close. Settings/Privacy + W6 own the inputs. Touching duration clamping, heartbeat threshold, or the foreground/background branch can resurface the "in-app dictation saved" or "ghost-trapped Dictate tap" regressions.

### Vocabulary & Correction
**Role.** On-device vocabulary biasing + an adaptive correction-review loop: a user-curated term list (file-backed) best-effort rescores finished Parakeet transcripts via a bundled FluidAudio CTC keyword-spotter (so domain words/proper nouns are recognized correctly); a plausibility/common-word **gate** decides which candidate corrections to apply; provenance of each applied correction is recorded so the user can review/confirm/revert it — including from the keyboard's correction-review strip — and verdicts feed back to tune future biasing.
**Entry points.** `VocabularyRescorerHolder.rescore/.prepare`, `VocabularyStore.shared`, `rebuildVocabulary`, `VocabularyGate.apply`, `CorrectionProvenance.shared`, `CorrectionAsksPublisher.publish`, `CorrectionBridge.publishAsks/.enqueueVerdict`, `CorrectionInbox.drain`, `CorrectionStore`, `CommonWords.isCommon`, `VocabularyLearning.shared.apply`, `EditLearning.learn`, `VocabularyAddInbox.drain`.
**Invariants.**
- **One correction, one path (Learn from Corrections, jot-shared `VocabularyLearning`).** A correction is "when I say X, write Y", stored ONCE, visibly, as a sounds-like (alias) on the term in `vocabulary.txt`. EVERY surface calls `VocabularyLearning.shared.apply(Correction)` (`VocabCore+App.swift`): transcript Edit → Save (`EditLearning` over `EditLearner`), selection Add to Vocabulary, Find & Replace's learn offer, the review list (`CorrectionReviewModel.pick/undo` — receipts stored per verdict in provenance), keyboard deck verdicts (`CorrectionInbox` → `pick`), keyboard Add to Vocabulary (queues Codable `Correction`s in App Group `jot.vocab.pendingCorrections` → `VocabularyAddInbox`), Settings sounds-like chips (`.correct(termID:)` / `.forget`), teach-by-voice Save. `VocabularyStore` implements `VocabularyListWriting` (row writes by id; `isWritable` false when the file exists but can't be read). No surface writes aliases or the store's edit counters itself; the only other alias writes are teach-by-voice's phase-2 provisional test overlay and its rollback. `CorrectionStore.adjust/confirm/revert/noteBlockedKeep/suppressBlock` remain ask-RANKING/suppression only. **No learned auto-replace**: no "Always replace", no grant; "keep original" / editing a term back only pauses the pair (gate BLOCK). iOS Parakeet has no decode-time bias, so `DecoderVocabulary` pairs are not used; the CTC spotter keeps reading the whole list file (paused pairs are blocked by the gate, as on Mac).
- Rescore is best-effort, NEVER a correctness gate: `rescore()` returns nil and the caller treats nil + any thrown error identically by falling back to the raw TDT transcript (`TranscriptionService`).
- **Gate, not raw rescore.** `VocabularyRescorerHolder.rescore` does not apply CTC hits directly — `VocabularyGate.apply` filters each candidate through an acoustic **plausibility** ceiling (skeleton edit-distance) AND a **common-word** guard (`CommonWords` shim over `JotVocabCore`'s bundled dictionaries — 21 languages, ~24k words each, served from the package's resource bundle; a missing non-nil list LOUD-FAILS via the diagnostics sink rather than silently disabling the guard) before substituting. Applied substitutions are handed to `CorrectionProvenance.shared.record` (anchored, before the transcript id exists), then committed to the row at persist time.
- **Correction-review cross-process flow.** Main app: after publish, `CorrectionAsksPublisher.publish` maps provenance records into context-windowed "asks" and writes them via `CorrectionBridge.publishAsks` (App Group `jot.correction.asks`, keyed by dictation `sessionID`) + posts `correctionAsksReady`. The keyboard's `CorrectionReviewStrip` reads the asks for its session and, on a user tap, enqueues a verdict via `CorrectionBridge.enqueueVerdict` (App Group `jot.correction.verdicts`). The main app drains them with `CorrectionInbox.drain` (on launch/foreground), applying each through `CorrectionProvenance.setVerdict`/`CorrectionStore`. The in-app `CorrectionReviewSection`/`CorrectionReviewModel`/`MarkedTranscriptText` is the parallel app-side review surface. The keyboard NEVER runs the gate or rescore — it only reads pre-resolved asks and writes verdicts back (the one sanctioned keyboard→main-app write-back besides terminal warm-hold/correction actions).
- **Preview ticks skip all of this** — see the Transcription subsystem's "NO vocabulary rescore on preview ticks" invariant; rescore/gate/provenance run ONLY on the saving stop-pass.
- Two-class split is deliberate: `VocabularyStore` (`@MainActor @Observable`) owns the term list + on-disk file; `VocabularyRescorerHolder` (actor) owns the live CoreML/FluidAudio handles. Don't merge them.
- Persistence is the plain-text "simple format" (one term/line, colon-then-comma aliases, `#` comments) because `CustomVocabularyContext.loadFromSimpleFormat` consumes that exact file. Don't change the format.
- The vocab file lives in the MAIN APP's `Application Support/Vocabulary/vocabulary.txt`, NOT the App Group; the keyboard never reads it.
- `rebuildVocabulary` uses a monotonic `generation` token to guard actor reentrancy — a stale rebuild discards its result after `await`.
- The CTC 110M boost model (~100 MB) ships BUNDLED in the IPA and loads via `CtcModels.loadDirect`; there is NO download/retry/progress path (`removeCache()` is a no-op). On a healthy install status is always `ready`.
- `VocabTerm.aliases` are the sounds-likes: shown as removable chips on each Settings row; every learned correction lands there.
- Master toggle (`jot.vocabulary.enabled`) only controls whether biasing is APPLIED; the list/file is always preserved. Off ⇒ `unload()`, on ⇒ `prepare()`.
**Blast radius.** Consumed by `TranscriptionService.swift` (batch-finalize ONLY, after TDT inference and before `ParagraphSegmenter` — so every batch caller gets biasing; the preview path deliberately does not). Driven by `VocabularySettingsView` (list) + the correction-review surfaces (`CorrectionReviewSection` in-app, `CorrectionReviewStrip` in the keyboard). Shares the bundled Parakeet directory but loads the CTC aux bundle independently. The correction-review loop NOW couples to the keyboard via `CorrectionBridge` (App Group asks/verdicts + `correctionAsksReady`) — but the vocab term file/biasing model stays main-app-only. Still no off-device transmission.

### Source-audio retention & backup
**Role.** Two on-device data-durability surfaces added with the multilingual arc: a **3-day source-audio retention** store that keeps every recording's 16kHz-mono audio so a saved transcript can be RE-TRANSCRIBED in another language within the window, and a manual **transcript export/import** (independent of iCloud Backup).
**Entry points.** `RetainedAudioStore.save/.url/.hasAudio/.purgeExpired`, `BackupExclusion.excludeRetainedAudio`, `TranscriptBackup.exportData/.importData`, `TranscriptDetailView.retranscribe(in:)`.
**Invariants.**
- `RetainedAudioStore` writes 16kHz-mono WAV under the App Group `RetainedAudio/` directory (NOT the SwiftData store), keyed by transcript `id`, written from `TranscriptStore.append` (live samples or by copying an imported file). It is **backup-excluded** — `BackupExclusion.excludeRetainedAudio()` runs a per-launch recursive sweep from `JotApp.init` (right after `excludeFluidAudioModels()`) — and **launch-purged** past `retentionDays` (3) via `RetainedAudioStore.purgeExpired()`, also called from `JotApp.init`.
- Re-transcribe is the SOLE retained-audio consumer: `TranscriptDetailView` shows the affordance only when `RetainedAudioStore.hasAudio(for:)`, and `retranscribe(in:)` re-runs the speech model on the kept audio in the chosen `LanguageChoice`, overwriting the transcript text + `language`. After the 3-day purge the affordance disappears; the saved text is untouched.
- `TranscriptBackup` is `#if JOT_APP_HOST` (app-target only): a single JSON `Envelope` of all transcripts (Original + Rewrite + provenance fields), surfaced in Settings → Your Data. Import is **idempotent** — it dedups by transcript `id`, so re-importing never duplicates. It is NOT iCloud sync and does not export prompts/vocab/preferences.
**Blast radius.** `RetainedAudioStore` is written by `TranscriptStore.append` and deleted alongside transcript deletes; read by `TranscriptDetailView` (re-transcribe → `TranscriptionService`). `TranscriptBackup` reads/writes the same Transcript store via `JotModelContainer.shared`. Both ride `BackupExclusion`/`JotApp.init` for residency. Changing the retention window, the WAV format (must stay 16kHz mono for Parakeet), or the backup-exclusion sweep touches privacy copy (`features.md §13.4`) and the re-transcribe feature (`§3.11`).

### Share Extension ("Send to Jot")
**Role.** A third recording-extension target (`JotShareExtension`, `com.apple.share-services`) that makes Jot a native iOS Share Sheet destination for audio files (`features.md §10.6`). Model B (locked in `docs/share-audio-to-jot/design.md`): the extension never opens the app or transcribes — it only stages shared audio bytes into the App Group and shows a brief confirmation; the MAIN APP drains the queue on its own next foreground.
**Entry points.** `ShareViewController` (extension side, stages into `AppGroup.pendingSharesDirectory()`), `PendingShareDrainer.drain()` (app side, called from `JotApp` on `scenePhase == .active`).
**Invariants.**
- The extension copies attachment **bytes** into the App Group, never hands the app a `URL` from its own sandbox — cross-sandbox file URLs are unreadable by `AVAudioFile` (`ExtAudioFileOpenURL` → `-54`), the same trap `TranscribeAudioFileIntent` already worked around.
- `PendingShareDrainer.drain()` is re-entrancy-guarded and defers while `RecordingService.shared.isRecording` — it never contends with a live dictation for the shared `@MainActor` `TranscriptionService`. A transcribe failure leaves the file staged to retry on the next foreground (durable queue, not fire-and-forget).
- Runs the SAME pipeline as every other transcription surface (`TranscriptionService.transcribe(audioFileURL:)` → optional Automatic Cleanup → `TranscriptStore.append(source: "share", retainAudioFileURL:)`) — no divergent code path, and the source audio is retained so a shared import can be [re-transcribed](#source-audio-retention--backup) if the language guess was wrong.
- **`NSExtensionActivationRule` (in both `Resources/ShareExtension-Info.plist` and `project.yml`'s `JotShareExtension` target) had a real, shipped-for-months bug** — found and fixed 2026-07-04: a stray `$` turned the final `extensionItems.@count` comparison into a reference to an unbound predicate *variable*, which threw on every evaluation and meant the extension could never activate for ANY file. Verified the fix with a standalone `NSPredicate` harness before shipping (build 236) — don't reintroduce the `$` if this predicate is ever touched again.
**Blast radius.** Shares `TranscriptionService`/`CleanupService`/`TranscriptStore` with every other capture surface — a change to any of those affects this path too. The extension target itself only links `Shared/` + its own `ShareExtension/` sources (no FluidAudio/MLX), matching the keyboard's dependency discipline.

### Speaker Notes (diarization)
**Role.** Speaker Notes is now a **real product feature** (`features.md §3.12`), not a hidden lab — the `diarizationLabEnabled` 5-tap flag and its `DiarizationLabView`/`DiarizationResultSheet` surfaces were DELETED. "Detect speakers" is a standard entry in the transcript-detail overflow menu whenever retained audio exists, and Share-Extension imports are auto-diarized. Built on the same offline-VBx foundation (FluidAudio's `OfflineDiarizerManager`, ~22 MB, no separate hardware gate). The Voice-Clone/TTS surfaces built on the same voiceprint foundation stay **paused** (owner 2026-07-04, `SettingsView.ttsFeatureEnabled = false`) — see `known-bugs-and-plans.md`'s "TTS Lab" entry before touching them; the 5-tap-Version reveal now keeps only Voice-Clone Consent.
**Engine (2026-09-27).** NVIDIA Nemotron 3 Diarization via FluidAudio 0.17.4 `Nemotron3Diarizer` (`fast128`, ~190 MB, OpenMDW-1.1), replacing pyannote/VBx — same move as Jot for Mac (its `docs/speaker-diarization/nemotron-migration.md`). Frame probabilities → `DiarizationProjection` (ported verbatim from Mac: exclusive argmax projection, 6 s solo gate, phantom fold, merge/coalesce, gap fill, 1.2 s short-run fold) → anonymous "Speaker N" labels by first appearance. No voice fingerprint, so owner "You" labeling, `OwnerVoiceprintStore` and `VoiceCloneGuard` were removed (owner decision); the pyannote model folder and the voiceprint defaults key are deleted once at launch (`DiarizerHolder.removeRetiredFiles`).
**Entry points.** `DiarizerHolder.diarize` (→ `(runs: [DiarSegment], duration)`) / `.prepareIfNeeded`, `DiarizationLabeling.persistedRows(runs:duration:transcriptText:)` (nil = single speaker), `PersistedSpeakerRow.encode`/`.decode`.
**Invariants.**
- **Diarization is an ENHANCEMENT, never a gate.** A shared-audio import that fails, is busy-skipped, or produces a single speaker is saved exactly as it would be without diarization — same tolerant posture as the optional cleanup pass. The auto-diarize hook re-checks `TranscriptionService.isBusy` / `RecordingService.isRecording` immediately before diarizing and **skips (does not wait)** if a dictation started mid-drain (FluidAudio's shared CoreML/BNNS state is unsafe under two concurrent graphs); the user can still run Detect speakers manually.
- **Persistence = the V9 `diarizationJSON` field** (a JSON `[PersistedSpeakerRow]`), stored ON the transcript so it deletes/cascades for free. Rows hold the display label ("Speaker 2"; pre-Nemotron rows may say "You") frozen at detection time and never relabel an existing transcript. The stored result is **invalidated** (`updateDiarization(id:, nil)`) whenever the underlying text/language changes (`retranscribe` success, or an Original-tab edit that actually changed the text) — the rows distribute the OLD text and can't be cheaply re-derived. The Speakers tab's visibility keys off `diarizationJSON != nil`, decoupled from `hasRewrite` (a call recording with cleanup off still gets its tab).
**Blast radius.** `PendingShareDrainer` now runs the auto-diarize hook after its shared `TranscriptionService`/`CleanupService`/`TranscriptStore.append` — a change to that import pipeline touches Speaker Notes too. `TranscriptDetailView`'s "Detect speakers" shares ONE overflow menu with Re-transcribe. `VoiceCloneRecorderView` calls `VoiceCloneGuard` before `TTSService.cloneVoice`. The diarizer model downloads to `OfflineDiarizerModels.defaultModelsDirectory()` (Application Support, separate from ASR's own FluidAudio cache) and is covered by the existing FluidAudio backup-exclusion sweep.

## Cross-process boundaries & invariants

These are the immutable structural rules. Violating one is a class of bug, not a one-off.

1. **Frozen versioned schema.** Never edit a shipped `JotSchemaVN.swift`; add `V(N+1)` + a `MigrationStage` + bump `versionIdentifier` and the `Transcript` typealias. `scripts/check-schema-frozen.sh` enforces it. Logical (not `@Relationship`) joins keep derived rows rebuildable.
2. **Keyboard 60 MB / no-inference.** The JotKeyboard target must not link FoundationModels or FluidAudio, and must never open a ModelContainer. ALL inference — rewrite/cleanup AND the live-preview re-transcribe loop — and all SwiftData access live in the main app; the keyboard remote-controls via deep link + Darwin notification, mirrors the preview/loading projections (`streamingPartialText`/`streamingLoadingVariantLabel`), reads history from a JSON mirror, and writes back only the three sanctioned slots (warm-hold actions, correction verdicts, keyboard-active heartbeat).
3. **App-Group / Darwin contract.** The App Group is the only cross-process channel. UserDefaults is atomic per-key only ⇒ multi-field handoffs are single JSON blobs. Darwin notifications are signals ("re-read"), never truth ⇒ correctness comes from projection state + a freshness heartbeat. Writer = main app, reader = keyboard/watch; readers never write back. Each projection has its own deliberately-different staleness window.
4. **Only feedback and Apple Intelligence leave.** The user-initiated feedback POST is Jot's sole outbound transmission (donations is a read-only GET); on iOS 27 Ask — and a rewrite too long for the on-device model — go to Apple's Private Cloud Compute via FoundationModels (end-to-end encrypted, not stored, not readable by Apple or Jot). Transcription and the warm-hold buffer never leave the device. Keep the caveat synced across privacy copy (Settings caption/footer, Settings.bundle, Help, wizard, App Store).
5. **Warm-hold orthogonality.** Warm hold is a start-faster optimisation only; it must never change WHERE a dictation goes. Foreground + warm window ⇒ inline insert (no save); only not-foreground takes the warm-resume capture path. Liveness needs both `warmExpiresAt` (in `PipelinePhaseProjection`) future AND a fresh `liveness` stamp.
6. **Source-based hero routing.** The recording hero presents from exactly three triggers (FAB, cold `jot://dictate`, return pill); nothing adopts `isRecording`. In-Jot keyboard taps start a background capture and present no hero.
7. **Capture-first cold start.** When the speech model isn't loaded, start the mic immediately and await the model at stop time — nothing said during the ~30s cold load is lost. The batch preview honours this too: `PreviewScheduler`'s `modelReady` latch HOLDS the captured window (firing no ticks) until `TranscriptionService.isPreviewModelReady`, then drains it into the preview.
8. **Save/no-save decided at the STOP site.** Fate is not stamped at recording birth: stop outside Jot / from the hero ⇒ persist; in-Jot field stop ⇒ `transient` publish without persisting. Gated on `applicationState == .active`.
9. **Publish-first pipeline.** Derive text → publish to clipboard → append to ledger best-effort. A persistence throw must never gate the publish. `transcriptReady` means "published", not "persisted" — reload off `historyMirrorUpdated`.
10. **Single shared singletons.** `RecordingService`/`TranscriptionService` are process-wide `.shared`; headless intents reuse them. `JotApp.init` does no blocking I/O and resets `PipelinePhaseProjection` on launch.

## Keeping this current

- Update this file on **subsystem or boundary changes only** — a new subsystem, a moved boundary, a changed cross-process contract, a new invariant. Do **not** churn it on ordinary file edits; it is intentionally coarse so it survives refactors.
- Treat **drift as broken**: a row pointing at a moved file or a stale invariant is worse than no map. If you split/merge/rename a subsystem, fix the Code map table, the Subsystem note, and any Searchable anchor in the same change.
- This is the WHERE companion to `features.md` (the WHAT). When a change alters behaviour, **pair the edit**: update the relevant `features.md §` and the matching row/note here together, and re-check the `features.md §` links still resolve.
- The Cross-process boundaries section is the highest-value, slowest-changing part — review it whenever you touch the App Group keys, Darwin notification names, the schema, the keyboard link list, or the warm-hold/hero/save-fate routing.
